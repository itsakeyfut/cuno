# cuno 本体の内部構成

## クレート構成

Rust のワークスペースで、役割ごとにクレートを分ける。

| クレート | 役割 | 時期 |
|---|---|---|
| `cuno` | 単一バイナリの本体。プロセスから入力を集めて `cuno-cli` を呼び、返った終了コードで終わる（`src/main.rs` だけ） | MVP |
| `cuno-cli` | CLI。コマンド引数の解釈、設定の解決、各コマンドへの振り分け、エラーの表示と終了コードの決定。コマンドごとのモジュールが各クレートを組み合わせる（[`src/` と `cuno-cli` に置くもの](#src-と-cuno-cli-に置くもの)） | MVP |
| `cuno-core` | 複数のクレートが共通で使う 6 つだけ：エラーと終了コードの分類、出力（cargo 風の表示・色・詳細度）、cuno home の解決、環境変数の一覧、パスの同一性、ビルドしたプログラムの起動 | MVP |
| `cuno-manifest` | `cuno.toml` / `config.toml` の読み込みと検証（[manifest.md](manifest.md)） | MVP |
| `cuno-toolchain` | コンパイラ抽象化（インターフェース）、検出、各コンパイラの実装、フラグ翻訳（[toolchain.md](toolchain.md)） | MVP |
| `cuno-build` | ビルドグラフの構築・実行、差分判定、compile_commands.json の出力（[build.md](build.md)） | MVP |
| `cuno-test` | テストの検出・実行・結果表示（[testing.md](testing.md)） | MVP |
| `cuno-tools` | fmt / lint（clang-format / clang-tidy の呼び出し）（[dev-tools.md](dev-tools.md)） | MVP |
| `cuno-script` | Lua ビルドスクリプトの組み込み | 後 |
| `cuno-deps` | 依存の解決・取得・ロックファイル（[dependencies.md](dependencies.md)） | 依存管理 段階 1 |

- `cuno-build` の中で、「ビルドグラフの構築」と「グラフの実行」をモジュールとして分ける（将来の Ninja バックエンドの余地）。
  - グラフのノード（コンパイルなどの 1 手順）は、実行するプログラム・引数・入力・出力に加え、手順の種類（ソースを指定したコンパイル、リンク、独自の手順）と、ヘッダの依存の調べ方（なし、depfile、MSVC の JSON、`/showIncludes`）を持つデータにする。種類と調べ方は、引数を読み直して推測せず、`cuno-toolchain` が決めた値として持たせる。
    - 環境変数と作業ディレクトリは、いまはすべての手順で同じ（コンパイラの環境と、プロジェクトのルート）なので、手順ごとには持たない。手順ごとに違うものが要るのは独自の手順（M7）で、そのときに手順へ持たせる。
    - 手順の種類で振る舞いを変える箇所は、すべて種類を網羅する `match` で書く。新しい種類（M6 のアーカイブ、M7 の独自の手順）を足したとき、答えていない箇所がコンパイルエラーになるようにするため。
    - 理由: compile_commands.json と将来の Ninja バックエンドを、グラフを実行せずにグラフから作れるようにするため。どちらも、どの手順がどのソースのコンパイルかと、ヘッダの依存の調べ方を必要とする。

### `cuno-core` に置くもの

次の 6 つに限る。ほかのものを足すときは、本仕様書を先に変える。

| もの | 内容 |
|---|---|
| エラーの分類 | 終了コードの分類（1: 利用者のコード・成果物の問題、2: 使い方の誤り、3: 設定・環境の問題、101: cuno 自身の内部エラー。[commands.md](commands.md#終了コード)）と、各クレートのエラー型が実装する共通のトレイト（分類と、任意の `help:` を返す）。表示は `cuno-cli`、プロセスの終了は cuno 本体が、それぞれ 1 か所で行う |
| 出力 | cargo 風の進捗表示（`Compiling` / `Finished` / `Running`）、警告とエラー、色と詳細度（`[term]`、`NO_COLOR`）。各クレートは直接表示せず、これを通して書く |
| cuno home | cuno home の場所の決定（[distribution.md](distribution.md#管理ディレクトリ) のとおり） |
| 環境変数の一覧 | cuno 本体が集めた環境変数を、ライブラリへ値として渡すための型。Windows では名前の大文字・小文字を区別せずに引く |
| パスの同一性 | 2 つのパスが同じ場所か、一方が他方の中にあるかを判定する、ただ 1 つの方法（[project-layout.md](project-layout.md#ソースの集め方とリンク)）。ソースの分類、出力先の確認、Visual Studio の場所の照合がこれを使う。理由: 同じ問いに綴りの比べ方を変えた答えが複数あり、使う場所が増えるたびに同じ種類の誤りを別々に直していたため |
| ビルドしたプログラムの起動 | cuno がビルドした実行ファイルを起動するときの、環境変数（cuno が受け取ったものだけ。コンパイラ用の環境は渡さない）、作業ディレクトリ（プロジェクトのルート）、表示するパス（現在のディレクトリからの相対）の決め方（[commands.md](commands.md#cuno-run)、[testing.md](testing.md#実行)）。`cuno run` とテストの実行が使う。標準入出力の扱い（`cuno run` はつないだまま、テストは取り込む）は使う側が決める。理由: 2 か所に書かれていて、一方の表示を後からもう一方に合わせ直したため |

- 環境変数の一覧を置く理由: コンパイラの検出・cuno home の解決・設定の読み込みがいずれも環境変数を必要とし、ライブラリは環境変数を値として受け取る（[クレート間の依存](#クレート間の依存)）。Windows で名前の大文字・小文字を区別しない引き方を、各クレートで書き直さないため。
- 理由: ライブラリのクレートは cuno 本体に依存できない。共通の置き場がないと、各クレートが終了コードや表示を独自に決めるか、`cuno-cli` が全クレートのエラーを知って終了コードに対応づけることになる。後者では、対応を書き忘れたエラーが黙って終了コード 1 になる。

### `src/` と `cuno-cli` に置くもの

`src/` には `main.rs` だけを置く。`main.rs` は、プロセスからしか得られないもの（コマンド引数、環境変数、カレントディレクトリ、ホスト、一時ディレクトリの場所、標準出力・標準エラーとそれぞれが端末か）を集めて `cuno-cli` に渡し、返った終了コードでプロセスを終える。プロセスを終えるのは `main.rs` だけとする。

`cuno-cli` には次だけを置く。

- `lib.rs`: コマンド引数の解釈（受け取った値を clap で解釈し、ヘルプとエラーは受け取った出力先に書く）、設定の解決、各コマンドへの振り分け、エラーの表示と終了コードの決定。
- コマンドのモジュール。下の表のものに限る。
  - 各クレートを組み合わせて呼び（本物の実装を選んで渡すことを含む）、結果を表示するだけとする。値を渡せばクレートが答えられる規則（名前の規則、診断の判定、パスの決め方など）は持たない。
  - そのコマンドだけが使うデータ（`cuno new` のテンプレート）は埋め込んでよい。

複数のコマンドが使うものは `cuno-cli` に置かず、[共通のルールの持ち主](#共通のルールの持ち主) のクレートに置く。

コマンドのモジュールは次の表のものに限る。`tests/architecture.rs` がこの表を読み、`cuno-cli` のモジュールが表と一致しないと失敗する。コマンドを足すときは、この表に行を足す（`fmt` と `lint` は、`cuno-tools` を呼ぶモジュールになる）。

| モジュール | コマンド |
|---|---|
| `build` | `build`、`check`、`run`、`test` |
| `clean` | `clean` |
| `doctor` | `doctor` |
| `fmt` | `fmt` |
| `lint` | `lint` |
| `new` | `new` |

- `build` が 4 つのコマンドを持つのは、[commands.md](commands.md#ビルド系コマンドbuild--run--check--testで使えるもの) のとおり 1 つのビルドの流れを共有するため。
- 理由: 複数のコマンドが共有する処理を置ける場所があると、どのクレートが答えるべきかを問わないまま処理が溜まり、規則が二重になる（ビルドと doctor が共有するツールチェーンの準備や、doctor がコンパイラの選択の順序を写し持っていたこと）。共有の置き場をなくし、置く場所を書く時点で決めさせる。また、`main.rs` だけがプロセスを読むことで、コマンドを値だけで呼べる。

## クレート間の依存

依存してよい向きを次に限る。`tests/architecture.rs` がこの表を読み、Cargo が解決した各クレートの依存（通常の依存とビルドスクリプトの依存。ターゲットごとの依存を含む）と照らし合わせて、表にない依存や、表にないクレートがあると失敗する。テストだけの依存（`[dev-dependencies]`）は、ビルドされるものの形を決めないので対象外とする。

- 「（後）」の行は、そのクレートを作るマイルストーンの設計で見直す仮の取り決めとする。

| クレート | 依存してよいクレート |
|---|---|
| `cuno-core` | なし |
| `cuno-toolchain` | `cuno-core` |
| `cuno-manifest` | `cuno-core`、`cuno-toolchain` |
| `cuno-build` | `cuno-core`、`cuno-manifest`、`cuno-toolchain` |
| `cuno-test` | `cuno-core` |
| `cuno-tools` | `cuno-core`、`cuno-manifest`、`cuno-toolchain` |
| `cuno-deps`（後） | `cuno-core`、`cuno-manifest`、`cuno-toolchain` |
| `cuno-script`（後） | `cuno-core`、`cuno-build` |
| `cuno-cli` | すべて |
| `cuno`（本体） | `cuno-cli`、`cuno-core` |

- **`cuno-manifest` が `cuno-toolchain` に依存し、逆はない。** コンパイラの種類と、フラグ翻訳が受け取る設定の型は `cuno-toolchain` が定義し、`cuno-manifest` は TOML をその型へ読み込む（`[build.<compiler>]` もコンパイラの種類で引く）。
  - コンパイラの種類について分岐する判断（引数の書き方、MSVC 系か LLVM 系か、LLVM のどのツールか）は、`cuno-toolchain` の 1 か所が、すべての種類を網羅する形で答える。ほかのコードは種類どうしを比べず、その答えを使う。新しいコンパイラは、答えていない判断があればコンパイルが通らない。
  - `cuno.toml` に書ける名前（`[build.<compiler>]`、`[toolchain.version]` のキー）は `cuno-manifest` が持つ。ビルドできないが名前として認めるコンパイラ（`gcc` / `safec`）を含むため。コンパイラの種類からこの名前への対応は `cuno-manifest` の 1 か所で行う。
  - 理由: コンパイラの抽象化に TOML の構造を持ち込まないため。コンパイラの追加が `cuno-toolchain` の変更だけで済む（[concept.md](../concept.md) の設計原則 5）。
- `cuno-test` はテストの実行と結果の表示だけを持つ。テストのビルドは `cuno-build` の 1 つのモードとする。
  - 理由: 渡された実行ファイルを動かして結果を集めるだけなので、設定やコンパイラを知る必要がない。
- `cuno-tools` には、「パッケージのコードの置き場」（[project-layout.md](project-layout.md#パッケージのコードの置き場)）にある対象ファイルの一覧と、compile_commands.json のパスを `cuno-cli` が渡す。一覧は `cuno-build` が、ソースの分類と同じ走査（出力先、ディレクトリのリンク、大文字・小文字の扱い）で作る。lint の対象は一覧で決まり、compile_commands.json は各ソースのコマンドを与えるだけ。`cuno-tools` は `cuno-build` には依存しない。
  - 理由: 走査を 2 つ持つと、出力先や別の名前の綴りの扱いが食い違う（ソースの分類で同じ誤りを何度か直している）。コマンドのモジュール（`cuno-cli`）は規則を持たないので、走査はソースの分類と同じ場所に置く。
- `cuno-build` は `cuno-deps` / `cuno-script` に依存しない。解決済みの依存やスクリプトの結果は、`cuno-cli` がデータとして渡す。
- **ライブラリのクレートは、プロセスの環境変数・コマンド引数・カレントディレクトリ・一時ディレクトリの場所を直接読まない。** cuno 本体（`main.rs`）が集めて値として渡す（環境変数の一覧を cuno home の解決やコンパイラの検出に渡す、など）。
  - 動いている OS（ホスト）も同じく、`cfg!` などで直接判断せず値として受け取る。ビルド対象の OS（ターゲット）は、[manifest.md](manifest.md) のとおりホストと区別する。MVP ではターゲット＝ホストとして本体が渡す。
  - 理由: テストで任意の環境を作れるようにし、ライブラリの振る舞いがたまたま動いているプロセスの環境に左右されないようにするため。ホストを値にするのは、Windows の CI でもほかの OS 向けの分岐をテストできるようにするため。

## 共通のルールの持ち主

複数のコマンドが使うルールは、次のクレートが 1 か所で持つ。各コマンドはそれを呼び、同じルールを書き直さない。

| ルール | 持ち主 |
|---|---|
| コマンド引数の解釈、設定の解決、各コマンドへの振り分け、エラーの表示と終了コードの決定 | `cuno-cli`（`cuno-core` の分類を使う） |
| プロセスからの入力の収集と、プロセスの終了 | `cuno` |
| エラーの分類、出力、cuno home、環境変数の一覧、パスの同一性、ビルドしたプログラムの起動 | `cuno-core` |
| プロジェクトの探し方、利用者が書いたパス（設定ファイルとコマンド引数）の解決、`cuno.toml` と設定ファイルの読み込み・検証、値ごとの優先順位、選ばれたコンパイラ・ターゲット・プロファイルに対する設定の重ね合わせ | `cuno-manifest` |
| コンパイラの種類、検出、選択の優先順位、Windows での環境解決、バージョンの条件、フラグ翻訳、ターゲットとホストの表し方 | `cuno-toolchain` |
| ソースの分類（エントリファイル・パッケージ本体・テスト）、cuno が決める出力先のパス、ビルドグラフ、テストのビルド、compile_commands.json、同梱ヘッダ、ビルドに使うコンパイラの準備（`cuno-toolchain` の検出・選択・環境の解決と、ビルドの設定による標準ライブラリの確認をつなぐこと） | `cuno-build` |
| テストの実行と結果の表示 | `cuno-test` |
| fmt / lint、`.clang-format` / `.clang-tidy` の生成 | `cuno-tools` |

- 設定は次の順で決まる。`cuno-manifest` が各層を読んで値ごとの優先順位を決め、`cuno-toolchain` がその結果からコンパイラを選び、`cuno-manifest` が選ばれたコンパイラ・ターゲット・プロファイルに対して `[platform.*]` / `[build.<compiler>]` / `[profile.*]` を重ねる。
- パスは持ち主を 2 つに分ける。利用者が書いたパス（設定ファイルやコマンド引数）をどこから解決するかは `cuno-manifest`、cuno が成果物をどこに置くか（`target/` の中の配置）は `cuno-build` が持つ。
  - 理由: 前者は設定の意味の問題、後者はビルドの都合の問題で、変わるきっかけが違う。

## リポジトリ構成

```
cuno/
├── Cargo.toml        # ワークスペース、かつ cuno パッケージ（バイナリ）
├── src/main.rs       # cuno バイナリ本体（src/ にはこれだけを置く）
├── crates/           # cuno 以外の上記クレート（ライブラリ。cuno-cli を含む）
├── tests/            # cuno 自体の結合テスト（実際にコンパイラを呼ぶ）
└── docs/specs/       # 仕様書
```

- 同梱ヘッダ（`test.hpp` / `test.h` / `test_main.c`）は `crates/cuno-build/headers/cuno/` に、`cuno new` が生成するサンプルは `crates/cuno-cli/templates/` に置き、それぞれビルド時にバイナリへ埋め込む。
  - 理由: crates.io に公開するパッケージには、そのクレートのディレクトリの中のファイルしか入らない。埋め込むファイルは、埋め込むクレートの中に置く必要がある。
- ルートはワークスペースであると同時に `cuno` パッケージでもある。
  - 理由: ルートの `tests/` は、ルートがパッケージでなければどのパッケージのテストにもならず、ビルドされない。ルートを `cuno` パッケージにすることで、`tests/` が cuno バイナリの結合テストとして動く。
  - あわせて、ルートで `-p cuno` を付けずに `cargo run` / `cargo install --path .` が使える。

## cuno 自体のテスト

- クレートごとのユニットテスト。
- 実際に MSVC / Clang を呼ぶ結合テスト（`tests/`）。
- CI: GitHub Actions の Windows ランナー（MSVC が入っている）。

## Rust

- edition 2024。
- **MSRV（最低サポートバージョン）は 1.88。**
  - 理由: edition 2024 で `let` チェーン（`if let Some(x) = a && b`）が使える最初のバージョン。設定の解決など、条件が重なる処理が多い cuno ではコードが大きく読みやすくなる。
  - cuno はビルド済みバイナリで配布するため、MSRV が影響するのはソースからビルドする利用者だけ。そのため、edition 2024 の最小（1.85）より新しくしても不利益は小さい。
  - MSRV を上げるのは意図的な変更とし、本仕様書を更新する。
- ツールチェーンは固定しない（`rust-toolchain.toml` を置かない）。CI で MSRV と stable の両方を確認する。
