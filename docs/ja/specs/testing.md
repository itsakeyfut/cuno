# テスト

## 方針: A + B

| | 内容 | 対象 |
|---|---|---|
| **A. cuno 独自テスト** | cuno が提供する軽量な仕組み | 新規プロジェクトの既定 |
| **B. 既存フレームワーク** | GTest / Catch2 / doctest 等をそのまま使い、cuno が検出・実行・表示を統一 | 既存資産を持つ利用者 |

- `cuno.toml` の `[test] framework` で選ぶ（[manifest.md](manifest.md)）。
- MVP は A のみ。

## 背景（調査）

- テストフレームワークの書き方への不満は少ない。主な不満はコンパイル時間（GoogleTest / Catch2 は include だけで 1 ファイルあたり数百 ms 以上、doctest は数十 ms 以下とされる。数値は主に doctest 側の公表値）。
- C++ 開発者の 3 分の 1 以上がユニットテストを書かず、17% はフレームワークを使わずに書いている（JetBrains「The State of C++ 2025」）。
- 以上から、ペインは書き方ではなく「導入の重さ」（フレームワーク導入・ビルドへの組み込み・登録）にあると判断した。

## A の要件

- **導入作業ゼロ**: `cuno new` 直後から cuno のテスト用ヘッダが使える。
- **書き場所は 2 通りとも許す**。利用者が好きな方を選べる。
  - **ソース内テスト**: Rust の `#[cfg(test)]` のように、実装ファイル内にテストを書ける。テストビルド時のみ有効で、通常ビルド / リリースビルドからは取り除かれる。
  - **`tests/` ディレクトリ**: 実装とは別のファイルに書ける。
- **軽量**: include によるコンパイル時間の増加を doctest 並み（1 ファイルあたり数十 ms 以下）に抑える。
- **モダンな書き方**: 大文字のマクロを並べる従来の書き方ではなく、C++20 ではマクロなし、C では小文字の書き方にする（下記）。
- `cuno test` で検出・ビルド・実行・結果表示まで行う。
- **テスト用ヘッダは cuno 本体に同梱して配布する**（Rust のテストハーネスが Rust ツールチェーンに同梱されているのと同様）。

### 推奨する書き分けと `cuno new` のサンプル

両方の書き方を許したうえで、テストの種類で書き場所を分ける方式（Rust と同じ）を推奨し、サンプルで見せる。

| テストの種類 | 書き場所 | 理由 |
|---|---|---|
| ユニットテスト（内部の関数を細かく確かめる） | 実装と同じファイル | 実装と一緒に直され、テストが古くなりにくい。外から見えない関数（C の `static` 関数など）もテストできる |
| 結合テスト（公開された使い方を外から確かめる） | `tests/` | 利用者と同じ立場で検証できる。内部を作り変えても壊れにくい |

- `cuno new` のサンプル: テスト付きの小さな関数を `src/calc.cpp`（C は `src/calc.c`）に置き、`src/main.cpp`（C は `src/main.c`）からその関数を呼ぶ。
  - `main` を持つファイル（エントリファイル）はテストビルドに含めないため、テストはエントリファイル以外に書く（[project-layout.md](project-layout.md) の「ソースの集め方とリンク」）。
  - 「ロジックとテストはパッケージ本体に書き、`main` は薄く保つ」という習慣もサンプルで伝える。
- `tests/` の使い方は、ライブラリプロジェクト対応時（後）のサンプルで見せる。MVP でも `tests/` に書いた結合テストは動く（パッケージ本体とリンクされる）。

## 書き方: 2 つの入口

テストの実行・結果表示の仕組みは共通。書き方の入口だけが言語・規格で分かれる。

| 入口 | ヘッダ | 対象 | 形式 |
|---|---|---|---|
| モダン API | `cuno/test.hpp` | C++20 以降 | マクロなし。名前空間 `cuno::test` |
| マクロ API | `cuno/test.h` | C（C11 以降）と C++17 | 小文字のマクロ。接頭辞 `cuno_` |

### 設計の理由

- cuno の主対象は C++（既定は C++20）。その表の顔を、マクロのないモダンな書き方にする。
- C++20 では、ラムダ・`std::source_location`（呼び出し位置の取得）・インライン変数によってマクロなしで書ける（boost-ext/ut が先行例）。
- C ではテストの登録や行番号の取得にマクロが不可欠。ただし C 標準の `assert` も小文字のマクロであり、小文字のマクロは C として自然。
- 大文字のマクロ名は入力の手間が大きい（Shift キーの多用）。小文字に統一する。
- 小文字の短い名前（`check`、`test` 等）をマクロにすると利用者の識別子と衝突するため、マクロには必ず `cuno_` を付ける。モダン API は名前空間で衝突を避ける。

### モダン API（C++20 以降）

```cpp
int add(int a, int b) { return a + b; }

#ifdef CUNO_TEST
#include <cuno/test.hpp>
static cuno::test::suite tests = [] {
    using namespace cuno::test;

    test("add works", [] {
        expect(eq(add(1, 2), 3));     // 失敗しても続行
        require(eq(add(0, 0), 0));    // 失敗したらこのテストを中断
    });
};
#endif
```

- ソース内テストは `#ifdef CUNO_TEST` で囲む（Rust の `#[cfg(test)] mod tests { ... }` と同じ形）。`tests/` 内のファイルは囲まなくてよい。
- `suite` は、中に書いたテストをプログラム開始時に登録する。

| API | 用途 |
|---|---|
| `suite` | テストのまとまり。静的変数として置くと、中のテストが自動で登録される |
| `test(名前, 関数)` | テストを 1 つ定義する。名前は文字列 |
| `expect(条件)` | 条件を確かめる。失敗しても続行する |
| `require(条件)` | 条件を確かめる。失敗したらそのテストを中断する |
| `eq` / `ne` / `lt` / `le` / `gt` / `ge(a, b)` | 比較。失敗時に両辺の値を表示する |
| `approx(a, b, 誤差)` | 浮動小数点数の比較 |
| `throws<例外型>(関数)` / `nothrow(関数)` | 例外が投げられるか（例外が有効なビルドのみ） |
| `info(...)` | 失敗時に一緒に表示する補足情報 |
| `skip(理由)` | そのテストをスキップ扱いにする |

- `expect(add(1, 2) == 3)` のように真偽値をそのまま渡すこともできるが、その場合は失敗時に値を表示できない。値を見たい場合は `eq` 等を使う。

### マクロ API（C / C++17）

```c
#include <cuno/test.h>

int add(int a, int b) { return a + b; }

cuno_test(add_works) {
    cuno_check_eq(add(1, 2), 3);     /* 失敗しても続行 */
    cuno_require_eq(add(0, 0), 0);   /* 失敗したらこのテストを中断 */
}
```

- `cuno_test` 等は、`CUNO_TEST` が定義されていないビルドでは自動で無効になる。テスト専用の補助関数は `#ifdef CUNO_TEST` で囲める。

| マクロ | 用途 |
|---|---|
| `cuno_test(名前)` | テストを 1 つ定義する。名前は識別子 |
| `cuno_check(式)` / `cuno_require(式)` | 式が真か。check は続行、require は中断 |
| `cuno_check_false(式)` / `cuno_require_false(式)` | 式が偽か |
| `cuno_check_eq` / `_ne` / `_lt` / `_le` / `_gt` / `_ge(a, b)` | 比較。失敗時に両辺の値を表示する（`cuno_require_` 版もあり） |
| `cuno_check_approx(a, b, 誤差)` | 浮動小数点数の比較 |
| `cuno_info(...)` | 失敗時に一緒に表示する補足情報 |
| `cuno_skip(理由)` | そのテストをスキップ扱いにする |

### 共通ルール

- **有効化 define**: テストビルド時、cuno が `CUNO_TEST` を定義する。
- **通常ビルドでの警告**: テストが原因の警告（未使用の関数など）を出さない。
- **通常ビルドとランタイム**: 通常ビルドは同梱のランタイムをリンクしない。C++20 以降の入口は、通常ビルドでは、ランタイムの関数を何もしない形で自分で持つ（GCC は、最適化しないとき、呼ばれない suite の中のテストもコンパイルし、ランタイムを参照するため）。そのため、`CUNO_TEST` なしでコンパイルしたオブジェクトとランタイムを 1 つのプログラムにリンクすると、GCC では同じ名前の定義が重なってリンクエラーになる。cuno のビルドはこの組み合わせを作らない（テストビルドはすべてのソースを `CUNO_TEST` でコンパイルする）。
- **例外が無効なビルド**: ゲーム開発では例外を無効にしてビルドすることが多い。`require` / `cuno_require_*` によるテストの中断は、例外が無効でも動作すること。
  - 実現方法: テストは 1 テスト 1 プロセスで実行する（下記「実行方式」）ため、`require` が失敗したら結果を書いて、そのプロセスを終える。例外も `longjmp` も使わない。
- **登録**: テストは、プログラムの開始時の静的な初期化で登録する（モダン API は `suite` の静的変数、マクロ API は、プログラムの開始時に呼ばれる関数。MSVC の C では、その一覧を置く領域 `.CRT$XCU` に置き、Clang と GCC では `constructor` 属性を付ける）。cuno はソースを読んでテストを探さない。
  - 登録したテストは、ファイル、行の順に並べる（同じ位置のものは登録した順）。ファイルの中の初期化の順はコンパイラによって違う（GCC は後ろのものから初期化する）ため、どのコンパイラでも同じ順にする。
  - 理由: ソースの読み取りでは、マクロや `#if` を通したテストを見落とすことがある。見落とすと、書いたテストが実行されないまま成功と報告される。
- **同梱のランタイム**: 登録先と `main` は、ヘッダと一緒に同梱する C のソース（`cuno/test_main.c`）にあり、テストビルドの各実行ファイルにリンクする。両方の入口は、この C のインターフェイスに登録する。
- **言語の混在**: ファイルごとに、そのファイルの言語の入口を使う。C++ のパッケージの `.c` ファイルは `cuno/test.h`、C のパッケージの `.cpp` ファイルはその規格に合う入口（C++20 以降なら `cuno/test.hpp`）。どちらで書いたテストも同じランタイムに登録され、同じテスト実行ファイルで動く。
- **テストの同一判定**: 「名前」と「ソース上の位置（ファイル + 行）」の組で判定する。判定するのは cuno で、テスト実行ファイルが一覧で報告した登録ごとの位置を使う。
  - 同じ位置からの複数回の登録（ヘッダを複数の翻訳単位が include した場合）は 1 つにまとめる。
  - 位置のファイルが同じかどうかは、書き方ではなくファイルシステムで決める（[project-layout.md](project-layout.md) と同じ）。`"util.h"` と `"../src/util.h"` のように別の書き方で include した同じヘッダは、同じ位置。
  - 別の位置に同じ名前のテストがあれば、重複としてエラーにする。
- **ヘッダ内のテスト**: モダン API は上記の同一判定により 1 回だけ登録する。マクロ API ではヘッダ内のテストに対応せず、同じ位置からの複数回の登録を検出したらエラーで案内する。
  - MSVC の C では、マクロ API のテストの名前がプログラム全体で 1 つの名前（シンボル）になるため、同じ名前のテストが 2 か所にある場合とヘッダ内のテストは、cuno の案内ではなくリンクエラーになる。
    - 理由: 登録用の関数をリンカが捨てないようにするため。捨てられると、最適化したビルド（`lto = true`）でテストが 1 件も実行されないまま成功と報告される。
- **持たないもの（当面）**: サブケース（doctest の SUBCASE）、フィクスチャ専用の仕組み。共通処理は普通の関数で書く。

## 実行

- `cuno test [名前の絞り込み]`。
- **テスト実行ファイルの単位**: ソース内テストはパッケージごとに 1 つの実行ファイルにまとめる。`tests/` **直下**のファイルごとに 1 つの実行ファイル（cargo と同じ）。
  - `tests/` のサブディレクトリは、テスト同士で共有する補助コードの置き場所として扱う（それ自体はテスト実行ファイルにならず、`tests/` 直下の各テスト実行ファイルにリンクされる）。
  - `tests/` の実行ファイルにはパッケージ本体もリンクされるため、ソース内テストも登録される（[project-layout.md](project-layout.md) の「リンクの規則」）。cuno は、`tests/` の実行ファイルでは登録位置が `tests/` の中にあるテストだけを実行し、ソース内テストはソース内テストの実行ファイルでだけ実行する。
- テスト実行時の作業ディレクトリは**プロジェクトのルート**（`cuno run` と同じ）。
- テストは並列実行する。並列数は共通オプション `-j` で指定する（既定は CPU コア数）。
- テスト中の標準出力・標準エラー出力は両方とも捕まえ、失敗したテストの分だけ表示する。`--nocapture` で常に表示する。
- テストにタイムアウトは設けない（cargo と同じ）。止まったテストは利用者が中断する。
- 失敗が 1 つでもあれば、終了コードは 0 以外。

### 実行方式: 1 テスト 1 プロセス

- cuno はテスト実行ファイルを、**テストごとに別プロセスとして起動**する。プロセス単位で並列実行し、出力はプロセスごとに捕まえる。
- 理由:
  - 標準出力はプロセスに 1 つしかないため、同じプロセス内で並列に動くテストの出力は分けられない。プロセスを分ければ、「並列実行」と「失敗したテストの出力だけ表示」を両立できる。
  - 1 つのテストがクラッシュ（不正なメモリアクセス等）しても他のテストは続行し、そのテストだけを失敗として報告できる。C/C++ では特に重要。
- 代償: プロセス起動の分だけ遅い（Windows では 1 回あたり数 ms〜数十 ms）。テストが数千件規模で問題になった場合に備え、「1 プロセスでまとめて実行する」モードを後から追加できる余地を残す。

### cuno とテスト実行ファイルの約束事

| 引数 | 動作 |
|---|---|
| `--list` | 登録されたテストを、登録ごとに名前・ファイル・行・入口（モダン API / マクロ API）とともに報告する |
| `--exact <名前>` | 指定したテストだけを実行する |

- 結果は終了コードで返す（`0` = 成功、それ以外 = 失敗）。
- テストの一覧と各テストの結果（成功・失敗・スキップとその理由、失敗した確認の位置と値、`info` の補足）は、cuno が環境変数 `CUNO_TEST_RESULT` で渡したファイルに、cuno だけが解釈する形式で書く。標準出力・標準エラー出力は利用者のものとして捕まえて表示するだけで、cuno は中身を解釈しない。
  - 理由: 利用者の出力にどんな文字列が含まれても、結果を取り違えないため。一覧を標準出力に書くと、プログラムの開始時に何かを表示するライブラリがあるだけで、テストの名前が壊れて実行されなくなる。
- 結果のファイルを書かずに終わったテスト（クラッシュ、`exit` の呼び出しなど）は失敗とする。終了コードが 0 でも同じ。
- 失敗した確認のあとに `skip` したテストは失敗とする（スキップより失敗を優先する）。
- テストの名前と `CUNO_TEST_RESULT` のパスは、Windows でもコードページに関係なく受け渡す（日本語の名前やパスをそのまま使える）。

### 出力

cargo に倣う。

```
running 3 tests
test add works ... ok
test parse rejects empty ... FAILED
test slow path ... skipped

failures:
---- parse rejects empty ----
src/parser.cpp:42: eq(result, 0) failed
  left:  -1
  right: 0

test result: FAILED. 1 passed; 1 failed; 1 skipped; finished in 0.02s
```

- すべて標準エラーに出す（`Compiling` などほかの表示と同じ）。標準出力は、将来プログラムが読む形式の出力のために空けておく。
- テスト実行ファイルごとに、`Running` の行、`running <件数> tests`、各テストの行、失敗の詳細、`test result:` の行の順に出す。
- 各テストの行は、終わった順に出す（並列に実行するため、名前の順とは限らない）。スキップしたテストは、理由があれば `test slow path ... skipped (理由)` と示す。
- 失敗の詳細は `failures:` の下に、テストごとに `---- 名前 ----` の後、失敗した確認（`ファイル:行: メッセージ`。ファイルはプロジェクトのルートからの相対パス）、`info` の補足、捕まえた標準出力・標準エラー出力の順に出す。結果のファイルを書かずに終わったテストは、終了コードを `the test ended without reporting a result (exit code 3)` のように示す。Windows でクラッシュを表す終了コード（`0xC0000005` など、負の値になるもの）は 16 進で示す。
- `--nocapture` では、各テストの出力を、そのテストの行の直後にまとめて出す。並列に実行していても、2 つのテストの出力が混ざることはない。
- 一覧を取れないテスト実行ファイル（起動できない、`--list` が 0 以外で終わる、同じ名前のテストが別の位置にある、ヘッダ内のマクロ API のテスト）は、`error:` で示し、そのテスト実行ファイルのテストは実行しない。

## 後（MVP 外）

- **ベンチマーク**: `cuno bench` 用のヘッダを同梱する（テストと同じく、モダン API とマクロ API の 2 つの入口）。
- **サニタイザ**: `cuno test --sanitize address` のように指定する。使える種類はコンパイラにより異なる（MSVC は AddressSanitizer のみ、Clang は UndefinedBehaviorSanitizer 等も）。使えない組み合わせは分かりやすいエラーにする。
- **カバレッジ**: `cuno test --coverage` で HTML レポートを出す（Clang は llvm-cov を利用）。

## 範囲外

- モック機能は持たない（必要なら外部ライブラリを使う）。

## B の要件

- 導入（フレームワークの取得・ビルド）と実行は cuno が担う。
