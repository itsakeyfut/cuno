# プロジェクトの種類と構成

## 基本方針: 構成とコーディングルールは開発者に任せる

- C/C++ のディレクトリ構成やコーディングルールは**開発者が自由に決める**。cuno は特定の構成を強制しない。
  - 例: `include/` に公開ヘッダを分ける人、`src/` にヘッダと実装を同居させる人、Unreal Engine 流に `Public/` / `Private/` で分ける人。いずれにも対応する。
- 開発者は `cuno.toml` で、自分のプロジェクトに**制約を自由に設けられる**（公開ヘッダの場所、ソースの場所など）。

## 既定の構成 + 上書き可能

「強制しない」と「設定なしで動く（cargo の体験）」を両立する。

- `cuno.toml` に何も書かなければ、次の既定構成として**解釈する**（各場所が何として扱われるかの規則）。`cuno new` が実際に生成するファイルは [commands.md](commands.md) の「生成するもの」を参照（この図のすべてを生成するわけではない）。

```
mygame/
├── cuno.toml
├── include/mygame/   # 公開ヘッダ（ライブラリのみ）
├── src/
│   ├── main.cpp      # 実行ファイル（既定）
│   ├── lib.cpp       # ライブラリ（ライブラリ対応後。MVP ではパッケージ本体の 1 ファイルとして扱う）
│   └── bin/*.cpp     # 追加の実行ファイル
├── tests/            # 結合テスト
├── examples/
└── benches/
```

- すべての場所は `cuno.toml` で上書きできる（ライブラリの `sources` / `public-headers` による上書きは、ライブラリ対応と同じ「後」。MVP で上書きできるのは `[[bin]] path` と `include-dirs`）。例（Unreal Engine 流）:

```toml
[lib]
kind = "static"
public-headers = ["Public"]
sources = ["Private"]
```

## 成果物の数え方

- 1 パッケージ = **ライブラリ最大 1 つ + 実行ファイル複数**。
- ライブラリが複数必要な場合は**ワークスペース**で複数パッケージに分ける。
  - 例（ゲーム）: `engine`（ライブラリ）・`game`・`editor` の 3 パッケージを 1 ワークスペースに。
- 新規作成: `cuno new` は実行ファイル（既定）、`cuno new --lib` はライブラリ。
- **MVP は実行ファイルのみ**。ライブラリ（`[lib]`、`cuno new --lib`）は「後」。下記「ソースの集め方とリンク」により、ライブラリがなくても `tests/` の結合テストは成り立つ。

## ソースの集め方とリンク

### 対象ファイル

- `src/` 以下のソースをすべてコンパイルする。
- 拡張子で言語を判定する。
  - `.c`: C としてコンパイルする。
  - `.cpp` / `.cc` / `.cxx`: C++ としてコンパイルする。
- C と C++ の混在を許す。`[package] lang` と異なる言語のファイルは、その言語の既定の規格（C: `c17`、C++: `c++20`）でコンパイルする。
  - 理由: C++ のプロジェクトに C のライブラリ（`sqlite3.c` など）を同梱することはよくある。C++ としてコンパイルすると、型変換の規則の違いでコンパイルできないか、名前修飾が変わって C として呼ぶ側とリンクできない。
  - ヘッダ（`.h`）はコンパイルの対象ではない。`cuno fmt` が `.h` をパッケージの言語として扱うのは整形のスタイルのためで、この判定とは別（[dev-tools.md](dev-tools.md)）。

### エントリファイルとパッケージ本体

| 区分 | 該当するファイル |
|---|---|
| **エントリファイル** | `main` を持つファイル。`[[bin]]` の `path` で指定したファイル（既定は `src/main.cpp` / `src/main.c`）と、`src/bin/` 直下の C/C++ ソース（`[[bin]]` を書かない場合の自動検出。[manifest.md](manifest.md)） |
| **パッケージ本体** | `src/` 以下のソースのうち、次を**除いた**もの: エントリファイル、`src/main.*`、`src/bin/` 以下のすべて |

- `src/main.*` と `src/bin/` 以下は、`[[bin]]` を書いたかどうかに関係なく、**常にパッケージ本体から除く**。
  - 理由: `[[bin]]` を書くと自動検出が止まるため、除外しないと `src/main.cpp` 等がパッケージ本体として全実行ファイル・テストにリンクされ、`main` が重複する。
  - `[[bin]]` を書いた場合、`[[bin]]` に挙げられていない `src/main.*` / `src/bin/` 以下のファイルはビルドされない（cuno はその旨を警告する）。
- 次の場合はエラー（終了コード 3）にする。
  - 実行ファイルが 1 つもない（既定のエントリファイルがなく、`src/bin/` も空で、`[[bin]]` も書いていない）。
  - `[[bin]]` の `path` にファイルがない、または C/C++ のソース（`.c` / `.cpp` / `.cc` / `.cxx`）でない。
  - エントリファイルがプロジェクトの外にある。オブジェクトファイルの置き場は、プロジェクト内でのソースの位置から決めるため（[build.md](build.md#出力先ディレクトリ)）。
  - 2 つの実行ファイルが同じ名前になる（`[[bin]]` の `name` の重複や、自動検出した `src/bin/app.cpp` と既定の実行ファイル `app` など）。出力先で同じファイルになるため。Windows では大文字と小文字を区別せずに比べる（`Tool` と `tool` も同じファイルになるため）。
- Windows では、ファイルとディレクトリの名前を大文字と小文字を区別せずに扱う。`src/Main.cpp` も既定のエントリファイルであり、`[[bin]]` の `path` を `SRC/Main.cpp` と書いても `src/main.cpp` と同じファイルとして扱う。
  - 理由: 同じファイルを別の綴りで 2 回数えると、エントリファイルがパッケージ本体にも入り、2 回コンパイルされて `main` が重複するため。
- 2 つのパスが同じ場所かは、ファイルシステムがたどり着く場所で比べる。リンク（シンボリックリンク、ジャンクション）や短い名前（8.3 形式）は、たどった先の場所として扱う。まだないファイルやディレクトリは、ある部分までをたどり、残りを書いたとおりに続けた場所とする。cuno がこの判定を使うすべての場所（ソースの分類、出力先がプロジェクトの中か、Visual Studio の場所）で同じ。
  - 理由: 綴りだけで比べると、プロジェクトの中のリンクを経由して外を指す出力先を「中」と判定してしまう。判定の方法が場所ごとに違うと、ある場所で直した誤りが別の場所で再び起きる。
  - コンパイラに渡すパスや表示するパスは、書かれたとおりのまま。たどった先は比べるときにだけ使う。
  - オブジェクトファイルの置き場は、ソースのあるディレクトリをたどった先と、ソースファイルの名前が置かれた位置で決める。ソースファイル自体がプロジェクトの外を指すリンクでも、`src/` の中のソースとしてコンパイルする。一方、`[[bin]]` の `path` に外を指すファイルのリンクを書くと、エントリファイルがプロジェクトの外にあるのでエラーになる。
- `src/` の中のディレクトリへのリンク（シンボリックリンク、ジャンクション）は、中を読まずに警告する。
  - 理由: 循環するリンクで探索が終わらなくなるのを防ぎ、プロジェクトの外のファイルを黙ってパッケージ本体に入れないため。

### パッケージのコードの置き場

パッケージのコード（利用者が書く C/C++ のソースとヘッダ）がある場所を、次のディレクトリとする。`cuno fmt` / `cuno lint` の対象はここから決める（[dev-tools.md](dev-tools.md#対象ファイル)）。

- `src/`・`tests/`・`examples/`・`benches/`
- `[[bin]] path` で指定したファイルが上のどれにも入らない場合、そのファイルがあるディレクトリ

ただし、次は除く。

- 出力先（`--target-dir` などで変えた場合も、実際に使う出力先の絶対パスで判定する。[build.md](build.md#出力先ディレクトリ)）
- 自分の `cuno.toml` を持つサブディレクトリ（別のパッケージ）

- `include-dirs` は置き場に含めない。
  - 理由: `include-dirs` は第三者のヘッダ（`third_party/include` など）を指すことが多く、整形すると利用者のものではないファイルを書き換えてしまう。また `include-dirs` は `[platform.<OS>.build]` / `[profile.<name>.build]` で追加でき、値を決めるにはコンパイラとプロファイルの選択が要るが、`cuno fmt` はコンパイラなしで動く必要がある。
- 置き場はディレクトリだけで決まり、コンパイラ・プロファイル・ターゲットの選択に左右されない。

### リンクの規則

| 成果物 | リンクするもの |
|---|---|
| 実行ファイル | そのエントリファイル + パッケージ本体 |
| ソース内テストの実行ファイル | テストランナー + パッケージ本体（エントリファイルは含めない） |
| `tests/` の結合テストの実行ファイル（ファイルごと） | テストランナー + パッケージ本体 + そのテストファイル |

- **エントリファイルはテストビルドに含めない**。テストランナーの `main` と利用者の `main` の衝突を避けるため。
  - 検討した他の方式と不採用の理由:
    - テストビルド時に利用者の `main` を別名にする（`/Dmain=...`）: SDL3 は自身で `#define main SDL_main` を行っており衝突する。ゲーム開発では致命的。
    - リンカ設定でエントリポイントを差し替える: C ランタイムの初期化と絡み、コンパイラごとに壊れやすい。
  - エントリファイル内にテストが書かれている場合、cuno はそれが実行されないことを警告する。
- ライブラリの種類（static / shared / header-only）は `cuno.toml` の `[lib] kind` で指定する。
