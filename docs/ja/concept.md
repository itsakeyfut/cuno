# cuno コンセプト

## C/C++の開発体験を改善したい

cuno は、C/C++ 開発に必要なパッケージ管理・ビルド・ツールチェーン管理・テスト・整形・静的解析を、1 つのコマンドと 1 つの設定ファイルにまとめるツールです。

```
cuno new mygame
cd mygame
cuno run
```

## 名前の由来

**C** と **Uno**（スペイン語・イタリア語で「1」）を合わせた名前です。C/C++ の開発に必要なものがこれ 1 つで揃う、**唯一の C/C++ 開発ツール**になることを目指して名付けました。

## なぜ作るのか

Rust の開発者は、`cargo new` から始めて、`cargo build`・`cargo test`・`cargo fmt`・`cargo clippy` まで、迷わず一本道で開発できます。C/C++ にはそれがありません。

C/C++ でプロジェクトを始めるには、次のものを別々に選び、別々の書き方で設定し、つなぎ合わせる必要があります。

| やりたいこと | 今の C/C++ で使うもの |
|---|---|
| ビルド設定 | CMake（CMakeLists.txt、`.cmake`） |
| ビルド実行 | Ninja / MSBuild / Make |
| 依存ライブラリ | vcpkg / Conan / 手作業 |
| テスト | ctest + GoogleTest / Catch2 / doctest |
| 整形・静的解析 | `.clang-format` / `.clang-tidy` |
| 始め方 | Visual Studio や CLion の新規作成ウィザード |

その結果、次のペインが生まれています。

1. 設定が読みにくく、多くのファイルに散らばっている
2. IDE なしでは気軽に始められない
3. テストの仕組みが乱立している
4. `-Werror` / `/WX` のようなコンパイラごとの引数を覚える必要がある
5. ライブラリを追加するたびに、ハッシュ値を調べて設定を書く必要がある

これは個人の感覚だけではありません。ISO C++ の開発者調査では、依存ライブラリの管理が長年「最大のペイン」の上位にあり、CMake プロジェクトの管理も多くの開発者がペインに挙げています。
C++ 開発者の 3 分の 1 以上はユニットテストを書いておらず、その背景には「導入の重さ」があります。

cuno は、これらを **1 つのツールの体験** として解決します。

## ビジョン

### 成功の定義

**C/C++ の開発者が cuno をインストールしたら、cuno のコマンドだけで C/C++ のプロジェクトを作り、開発を進められること。**

### 将来像

最初は clang-format や clang-tidy などの既存ツールを cuno の中から呼び出します。
その後、それらを cuno 用に作り直したものへ少しずつ置き換え、四散しているツールから C/C++ の開発者を解放していきます。

### 3 年後の利用者像

1. **個人開発者**が cuno を使い、体験の良さを感じる
2. その人が**職場**でも cuno を使い始める
3. 実務で見つかった不具合が **Issue** として起票され、**PR** として改善が届く

個人の「使って気持ちいい」から、実務の採用、そして貢献へとつながる流れを目指します。
対象はゲーム開発をはじめとする実務の C/C++ 開発で、Windows と Visual Studio が中心の現場でも採用できることを重視します。

## 設計原則

### 1. cargo を基にする

機能と使い心地の基準は cargo です。コマンド体系、設定ファイルの考え方、出力の形式まで、cargo を使ったことがある人なら迷わない体験を目指します。
cargo の形が C/C++ に合わない部分だけ、C/C++ の事情に合わせて変えます。

### 2. 設定は 1 か所に集約する

プロジェクトの設定は `cuno.toml` に書きます。CMake のような専用言語ではなく、TOML で読み書きできる形にします。`.clang-format` や `.clang-tidy` を利用者が書く必要はありません。

### 3. 基本は設定なしで動き、必要なら変えられる

`cuno new` 直後は設定を 1 行も書かずに動きます。一方で、ディレクトリ構成やコーディングルールを cuno が強制することはありません。
`include/` を分ける人、`src/` に同居させる人、Unreal Engine 流に `Public/` / `Private/` で分ける人、どの流儀にも `cuno.toml` で合わせられます。

### 4. コンパイラの違いは cuno が吸収する

`warnings-as-errors = true` と書けば、MSVC には `/WX`、GCC / Clang には `-Werror` が渡ります。利用者がコンパイラごとのフラグを覚える必要はありません。足りない場合のために、生のフラグを書く逃げ道は残します。

### 5. 主要コンパイラをすべて平等に扱う

GCC・Clang・MSVC の 3 系統すべてを対象にします。Windows と MSVC を後回しにしません。新しいコンパイラは、1 つのインターフェースを実装するだけで追加できる設計にします。

### 6. モダンな C/C++ を前提にする

対象は C++17 / C11 以降、既定は C++20 / C17 です。テストは C++20 ならマクロなしで書けます。
古い慣習のために、新しく始める人の体験を犠牲にさせません。

### 7. 単一バイナリで完結する

cuno は 1 つの実行ファイルで動きます。CMake や Ninja を別途インストールする必要はありません。

### 8. 実務で使える現実的な判断をする

理想より、現場で動くことを優先します。たとえば次のような判断をしています。

- SDL3 の `#define main SDL_main` と衝突しないよう、テストのビルド方法を選んだ
- ビルド済みの依存ライブラリと混ぜてもリンクエラーにならないよう、C ランタイムの既定を選んだ
- 日本語版 Visual Studio でも動くよう、出力の言語に依存しない仕組みを選んだ

### 9. 複雑な設定も書け、黙って間違えない

大規模なプロジェクトの特殊・複雑な設定も書けるようにします。書き方は 3 段で、上の段で書けるものは上の段で書きます。`cuno.toml` の宣言、カスタムルール（`[[build.rule]]`）、Lua のビルドスクリプトの順です（[build.md](specs/build.md#カスタムビルド処理3-層構造)）。

どの段でも、書いたものと違う結果になりうるときは、推測せずエラーにします。たとえば次の場合です。

- ファイルに 1 つも一致しないパターン
- 宣言したのに作られなかった出力
- 重ね合わせの規則によらず、黙って変わる値（スクリプトが宣言を上書きする、など）
- 再ビルドの判定から漏れた入力

書けずにエラーで止まることより、成功と報告して違うことをする方が、利用者の信頼を深く損なうからです。既存のツールへの不満を調べると、多くはこの形でした（[調査](../research/build-tool-complaints.md)）。

学ぶことは少なくします。新しい概念は、必要になるまで求めません。設定を読む順序と、どの層が勝つかは、1 ページで説明します（[manifest.md「設定の重ね合わせ」](specs/manifest.md#設定の重ね合わせ)）。

## 何をしないか

- **既存の CMake プロジェクトとの共存は目指さない。** cuno は CMake を置き換えるものです。
- **ディレクトリ構成やコーディングルールを強制しない。** 既定はあるが、従わせはしない。
- **何でもできる汎用ビルドシステムにはしない。** C/C++ の開発に集中します。複雑な処理のためには Lua のビルドスクリプトという逃げ道を用意しますが、大半のプロジェクトがそれを使わずに済むことを目指します。逃げ道も、原則 9 のとおり黙って間違えないものにします。

## 既存のツールとの違い

cuno の設計は、既存ツールを使い比べた経験ではなく、**C/C++ 開発者のペインや意見の調査結果**をもとに、**cargo を基にして**組み立てています。C/C++ 向けのツールとの主な違いは次のとおりです。

| ツール | 特徴 | cuno との違い |
|---|---|---|
| CMake + vcpkg / Conan | 事実上の標準。対応範囲が最も広い | 複数のツールと書き方を組み合わせる必要がある。cuno は 1 つにまとめる |
| xmake | Lua でビルドを記述。パッケージ管理付き | 設定の中心が Lua スクリプト。cuno は TOML の宣言が中心で、Lua は逃げ道に限る |
| build2 | cargo に近い体験を目指す本格的なツールチェーン | 大規模・複雑なプロジェクト向けで、学習コストが高い。cuno は始めやすさを優先する |
| cabin（旧 Poac） | cargo に強く影響を受けたツール | cargo を目標にする点は同じ。cuno は Windows / MSVC を最初から主要な対象にし、ゲーム開発の実務を重視する |

## 長期的な展望

cuno は長期的に育てるプロジェクトです。

| 段階 | 内容 |
|---|---|
| MVP | Windows 11 + MSVC / Clang。`new` / `build` / `run` / `check` / `clean` / `test` / `fmt` / `lint` / `doctor` |
| MVP 直後 | GCC 対応、`cuno init`、ツールチェーンの一覧と選択 |
| 依存管理 | Git / URL 指定 → レシピインデックス（`cuno add sdl3`）→ 将来は公開パッケージサービス |
| その後 | ライブラリ・ワークスペース、Linux / macOS、クロスコンパイル（Android / WebAssembly）、IDE 連携、ビルドキャッシュ |
| 将来 | 自作フォーマッタ、コンパイラの自動インストール、C++20 モジュール |

### safec について

cuno の開発者は、メモリ安全な C/C++ を作る実験として、コンパイラ **[safec](https://github.com/itsakeyfut/safec)** も開発しています。
C/C++ に Rust の安全性（メモリ安全・スレッド安全・ライフタイム・所有権）をどこまで持ち込めるかを試すプロジェクトです。

cuno は、主要コンパイラで成立したあと、safec を Clang / MSVC / GCC と並ぶコンパイラの選択肢の 1 つとして扱う予定です。
