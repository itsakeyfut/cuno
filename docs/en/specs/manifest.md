# Configuration Files

## File layout

| File | Role | Cargo equivalent |
|---|---|---|
| `cuno.toml` | Project settings. Describes language, standard, compiler, test framework, dependencies, etc. | `Cargo.toml` |
| `.cuno/config.toml` | Machine-specific settings (compiler paths, output directory, etc.) | `.cargo/config.toml` |

Users write only these two configuration files (see the anti-goals in [overview.md](overview.md)). The following are exceptions:

- The user-level `<cuno home>/config.toml` (default `~/.cuno/config.toml`): same format as `.cuno/config.toml`, and applies to every project on that machine (see "Two levels of settings" below).
- Build script (Lua): an escape hatch for processing that cannot be expressed in declarative settings. Present only when needed ([build.md](build.md)).
- `cuno.lock`: a file generated by cuno; users do not write it ([dependencies.md](dependencies.md)).

## cuno.toml (MVP scope)

Overview. Comments describe each item and its possible values (when there is a fixed set of choices).

```toml
[package]
name = "mygame"            # Package name (required)
version = "0.1.0"          # Package version (required)
lang = "c++"               # Language (c / c++)
edition = "c++20"          # Language standard (c++17 / c++20 / c++23 / c11 / c17 / c23)
description = ""           # Description (optional)
license = ""               # License (optional, SPDX expression)

[toolchain]
compiler = "msvc"          # Compiler to use (msvc / clang / clang-cl / gcc / safec)

[toolchain.version]        # Per-compiler version constraints (msvc / clang / clang-cl / gcc / safec). Optional
msvc = ">=19.29"
clang = ">=17"

[build]
warnings = "all"           # Warning level (default / all / pedantic)
warnings-as-errors = false # Whether to treat warnings as errors (true / false)
defines = []               # Preprocessor definitions
include-dirs = []          # Additional include paths
links = []                 # System libraries to link (e.g. ["d3d12", "dxgi"])
lib-dirs = []              # Library search paths
link-flags = []            # Flags passed to the linker as-is
runtime = "dynamic"        # How the C runtime is linked (dynamic / static)
exceptions = true          # Whether to use C++ exceptions (true / false)
rtti = true                # Whether to use C++ RTTI (true / false)
precompiled-header = ""    # Precompiled header (optional)
unity = false              # Whether to use a unity build (true / false)

[build.msvc]               # Per-compiler raw flags (msvc / clang / clang-cl / gcc / safec)
flags = []

[platform.windows.build]   # Per-OS settings (windows / linux / macos / android / wasm)
defines = ["NOMINMAX"]

[profile.dev.build]        # Per-profile settings
defines = ["GAME_DEBUG"]

[[bin]]                    # Executables (multiple allowed)
name = "mygame"
path = "src/main.cpp"
subsystem = "console"      # Launch mode (console / windows)

[lib]                      # Library (at most one). Unused in MVP
kind = "static"            # Library kind (static / shared / header-only)
public-headers = ["include"]
sources = ["src"]

[test]
framework = "cuno"         # Test framework to use (cuno / gtest / catch2 / doctest)

[profile.dev]
opt-level = 0              # Optimization level (0 / 1 / 2 / 3 / "s")
debug-info = true          # Whether to emit debug info (true / false)
debug-assertions = true    # Whether to enable assert (true / false)
lto = false                # Whether to use link-time optimization (true / false)

[profile.release]
opt-level = 3
debug-info = false
debug-assertions = false
lto = false
```

For the `[fmt]` / `[lint]` items, see [dev-tools.md](dev-tools.md).

### Implemented in MVP

Items and values outside MVP fall into two categories by their behavior when specified.

**Warn and ignore** (ignoring them does not change the meaning of the build output):

- `[build] unity`, `[build] precompiled-header` (left at their defaults `false` / `""`, nothing is ignored, so there is no warning)
- `[alias]` and `[build] cache` in `.cuno/config.toml` (MVP does not use a build cache. The default value `auto` also has no effect in MVP)

**Error** (exit code 3. Ignoring them would silently build something different from what the user intended):

- `compiler = "safec"` (including when specified via `--compiler`, `CUNO_COMPILER`, or config.toml). It is an error only when it is the compiler selected; if a higher layer overrides it with another compiler, it is not an error (just as `[toolchain.version]` checks only the constraint of the compiler used).
- `[test] framework = "gtest"` / `"catch2"` / `"doctest"`
- Custom profiles (`inherits`, and `--profile` other than `dev` / `release`)
- `[lib]`
- `[[build.rule]]` (custom rules; the same when written under `[platform.<OS>.build]` / `[profile.<name>.build]`)
- `[target.<target>]` in `.cuno/config.toml`, `--target`
- `[dependencies]`

Everything else (including `[platform.<OS>.build]` and the `msvc` / `clang` / `clang-cl` / `gcc` keys of `[toolchain.version]`) is implemented. The `safec` keys of `[toolchain.version]` / `[build.<compiler>]` are harmless unless that compiler is used, so they do not cause an error if present.

### Unknown keys

- If `cuno.toml` / `config.toml` contains a key cuno does not know, it emits a **warning** and continues (not an error).
- Reason: so that an older cuno does not stop when reading items added in a newer cuno (same as Cargo).
- Warnings and errors about a configuration file show the file, line and column (e.g. `--> cuno.toml:12:1`), so that a misspelling and the like can be fixed at once.

### Locating the project and resolving paths

- cuno searches for `cuno.toml` from the current directory upward through parent directories, and treats the first location found as the project root (same as Cargo). `cuno build` etc. can be run from subdirectories.
- Relative paths written in a configuration file are resolved relative to **the location of that file**.
  - `include-dirs` / `lib-dirs` etc. in `cuno.toml`: relative to the project root.
  - `target-dir` etc. in `.cuno/config.toml`: relative to the parent of `.cuno/` (the project root).
  - User-level config.toml: relative to `<cuno home>`.
- On Windows, a path that starts with `\` or `/` without a drive (e.g. `/inc`), or that has a drive with no separator after it (e.g. `C:inc`), is an error (exit code 3). Write an absolute path or a relative one.
  - Rationale: where either points depends on the current drive or directory at the time, not on where the file is. Resolving it silently could let a build succeed while looking in a place the user did not mean.

## Item reference

### `[package]`

| Item | Required | Default | Description |
|---|---|---|---|
| `name` | Yes | — | Package name. Also the default executable name |
| `version` | Yes | — | Package version (Semantic Versioning) |
| `lang` | | `"c++"` | Language |
| `edition` | | C++: `"c++20"` / C: `"c17"` | Language standard |
| `description` | | none | Description |
| `license` | | none | License (SPDX expression, e.g. `"MIT OR Apache-2.0"`) |

Values of `lang`:

- `c`: A C project.
- `c++`: A C++ project.

Values of `edition`:

- `c++17`: C++17. Minimum supported C++ standard.
- `c++20`: C++20. Default for C++.
- `c++23`: C++23. Only if the compiler supports it.
- `c11`: C11. Minimum supported C standard.
- `c17`: C17. Default for C.
- `c23`: C23. Only if the compiler supports it.

An `edition` that does not match `lang` (e.g. `edition = "c++20"` with `lang = "c"`) is an error.

`edition` applies to sources in `lang`'s language. Sources in the other language (a `.c` in a C++ package, for example) are compiled with that language's default standard ([project-layout.md](project-layout.md#target-files)).

### `[toolchain]`

| Item | Required | Default | Description |
|---|---|---|---|
| `compiler` | | Automatic selection | Compiler to use. Selection precedence is in [toolchain.md](toolchain.md) |
| `version` | | No constraint | Per-compiler version constraints (see `[toolchain.version]` below) |

#### `[toolchain.version]`

Write a version constraint per compiler name. **Only the constraint for the compiler actually used** is checked (switching to another compiler via `--compiler` etc. does not fail on unrelated constraints).

```toml
[toolchain.version]
msvc = ">=19.29"     # cl.exe version (not the VS product version)
clang = ">=17"
```

- Keys: `msvc` / `clang` / `clang-cl` / `gcc` / `safec`.
- Values: a pair of a comparison operator `>=` / `>` / `<=` / `<` / `=` and a version. Multiple conditions can be combined, separated by commas (e.g. `">=17, <19"`).
- Matching compares **only up to the components written** (e.g. `"=19.40"` matches `19.40.33811`; `">=17"` matches `17.0.6`).
- Compilers not listed have no constraint (minimum versions follow [toolchain.md](toolchain.md)).

Values of `compiler`:

- `msvc`: Microsoft Visual C++ (cl.exe). Default for automatic selection on Windows.
- `clang`: Clang (`clang` / `clang++`, using GCC-style flags).
- `clang-cl`: Clang in MSVC-compatible mode (using MSVC-style flags).
- `gcc`: GCC. On Windows, MinGW-w64 GCC ([toolchain.md](toolchain.md#mingw-gcc)).
- `safec`: An experimental compiler developed separately by the cuno developer ([toolchain.md](toolchain.md)). Supported after cuno is established on the major compilers.

### `[build]`

| Item | Default | Description |
|---|---|---|
| `warnings` | `"all"` | Warning level |
| `warnings-as-errors` | `false` | Whether to treat warnings as errors |
| `defines` | `[]` | Preprocessor definitions (e.g. `["GAME_DEBUG", "VERSION=3"]`) |
| `include-dirs` | `[]` | Additional include paths |
| `links` | `[]` | System libraries to link. Write just the name, and cuno converts it to each compiler's form ([build.md](build.md#settings-and-flags)). Writing it with `.lib` is an error (exit code 3) |
| `lib-dirs` | `[]` | Library search paths |
| `link-flags` | `[]` | Flags passed to the linker as-is (escape hatch) |
| `runtime` | `"dynamic"` | How the C runtime is linked |
| `exceptions` | `true` | Whether to use C++ exceptions (ignored for C) |
| `rtti` | `true` | Whether to use C++ RTTI (ignored for C) |
| `precompiled-header` | none | Path of the header to treat as the precompiled header |
| `unity` | `false` | Whether to use a unity build |
| `target-dir` | `target/` | Output directory ([build.md](build.md)). Only in `[build]` (not in `[platform.<OS>.build]` / `[profile.<name>.build]`) |

Values of `warnings` (For the flags, see [build.md](build.md#settings-and-flags)):

- `default`: Only the compiler's default warnings.
- `all`: Enables the generally recommended warnings. Default. Starting new projects on the strict side makes life easier later.
- `pedantic`: In addition to `all`, requires strict standard conformance.

`warnings-as-errors`:

- `true`: Turns warnings into errors. Intended for CI.
- `false`: Warnings stay warnings. Default. So that the build does not stop on work-in-progress code.

Values of `runtime`:

- `dynamic`: Links the C runtime as a DLL. Default. All profiles use the release C runtime (the debug one is not the default; the reason is in [build.md](build.md#settings-and-flags)).
- `static`: Embeds the C runtime in the executable. No need to ship the runtime when distributing.

`exceptions`:

- `true`: Uses C++ exceptions. Default.
- `false`: Disables exceptions. A common setting in game development.

`rtti`:

- `true`: Uses RTTI (`dynamic_cast` / `typeid`). Default.
- `false`: Disables RTTI.

### `[build.<compiler>]`

An escape hatch for when the abstracted settings are not enough. Write raw flags per compiler name.

| Item | Default | Description |
|---|---|---|
| `flags` | `[]` | Flags passed to that compiler as-is |

Values of `<compiler>`:

- `msvc`: Passed only when using MSVC.
- `clang`: Passed only when using Clang.
- `clang-cl`: Passed only when using clang-cl. It accepts MSVC-style flags but also has its own flags, so it is kept separate from `msvc`.
- `gcc`: Passed only when using GCC.
- `safec`: Passed only when using safec.

### `[platform.<OS>.build]`

Per-OS settings. Accepts the same items as `[build]`.

```toml
[platform.windows.build]   # OS (windows / linux / macos / android / wasm)
defines = ["NOMINMAX"]
links = ["d3d12", "dxgi"]
```

Values of `<OS>`:

- `windows`: When building for Windows.
- `linux`: When building for Linux.
- `macos`: When building for macOS.
- `android`: When building for Android.
- `wasm`: When building for WebAssembly.

- Which OS a build is "for" is determined by the target (not the OS of the host).
- No conditional expressions like Rust's `cfg(...)` (they hurt readability). Only named tables.

### `[profile.<name>.build]`

Per-profile settings. Accepts the same items as `[build]`.

```toml
[profile.dev.build]
defines = ["GAME_DEBUG"]   # Added only for the dev profile
```

### Settings layering

Layered in this order:

1. `[build]`
2. `[platform.<OS>.build]`
3. `[build.<compiler>]`
4. `[profile.<name>.build]`

- List items (`defines`, `include-dirs`, `links`, `lib-dirs`, `link-flags`, `flags`): later settings are **appended**.
- Single-value items (`warnings`, `warnings-as-errors`, `runtime`, `exceptions`, `rtti`, `precompiled-header`, `unity`): later settings **override**.
- `flags` can only be written in `[build.<compiler>]`. `[build.<compiler>]` cannot be nested under `[platform.<OS>.build]` / `[profile.<name>.build]` (to avoid complexity).

### `[[bin]]`

| Item | Default | Description |
|---|---|---|
| `name` | `package.name` | Executable name. The same rule as `package.name` (ASCII letters, digits, `-` and `_`, starting with a letter); otherwise an error (exit code 3) |
| `path` | `src/main.cpp` (`src/main.c` for C) | Entry point source |
| `subsystem` | `"console"` | Launch mode (meaningful only on Windows) |

Values of `subsystem`:

- `console`: Launches as a console app. Default.
- `windows`: Launches without a console window. Essential for games. cuno also sets the entry point, so that you can keep writing an ordinary `main` instead of `WinMain` ([build.md](build.md#settings-and-flags)).

- If no `[[bin]]` is written: cuno auto-detects the default executable (`src/main.cpp` / `src/main.c`) and C/C++ sources directly under `src/bin/` (`*.c` / `*.cpp` / `*.cc` / `*.cxx`; one file = one executable, with the file name as the executable name).
- If at least one `[[bin]]` is written: **no auto-detection**. Only the ones written become executables (this prevents the default `src/main.cpp` from unintentionally being treated as an entry file and `main` from being duplicated).
- When there are multiple executables, `cuno run` without `--bin` is an error (exit code 2) and lists the names to choose from.

### `[lib]`

Not used in MVP. Only the item names are reserved.

| Item | Default | Description |
|---|---|---|
| `kind` | `"static"` | Library kind |
| `public-headers` | `["include"]` | Public header directories |
| `sources` | `["src"]` | Source directories |

Values of `kind`:

- `static`: Static library (`.lib` / `.a`). Embedded into the consuming executable.
- `shared`: Dynamic library (`.dll` / `.so` / `.dylib`). Loaded at run time.
- `header-only`: Header-only library. Has no compiled artifacts.

### `[test]`

| Item | Default | Description |
|---|---|---|
| `framework` | `"cuno"` | Test framework to use |

Values of `framework`:

- `cuno`: cuno's own testing (`cuno/test.hpp` for C++20, `cuno/test.h` for C / C++17). Works with no setup and supports in-source tests. Default. See [testing.md](testing.md) for details.
- `gtest`: GoogleTest. For users with existing test assets. Later.
- `catch2`: Catch2. Later.
- `doctest`: doctest. Later.

### `[profile.<name>]`

`dev` (default) and `release` are built in. Custom profiles are created by inheriting an existing one with `inherits` ([build.md](build.md)).

| Item | `dev` default | `release` default | Description |
|---|---|---|---|
| `opt-level` | `0` | `3` | Optimization level |
| `debug-info` | `true` | `false` | Whether to emit debug info |
| `debug-assertions` | `true` | `false` | Whether to enable `assert` |
| `lto` | `false` | `false` | Whether to use link-time optimization |
| `inherits` | — | — | Profile to inherit from (custom profiles only) |

Values of `opt-level` (For the flags, see [build.md](build.md#settings-and-flags)):

- `0`: No optimization.
- `1`: Light optimization.
- `2`: Standard optimization.
- `3`: Maximum optimization.
- `"s"`: Optimize for size.

`debug-info`:

- `true`: Emits debug info.
- `false`: Does not emit it.

`debug-assertions` (same name as Cargo):

- `true`: Enables `assert` (does not define `NDEBUG`).
- `false`: Disables `assert` (defines `NDEBUG`).

`lto`:

- `true`: Uses link-time optimization. Opt-in because it lengthens link time.
- `false`: Not used. Default (same as Cargo).

## .cuno/config.toml

### Two levels of settings

| Level | Location | Scope | Git |
|---|---|---|---|
| Project-level | `<project>/.cuno/config.toml` | That project | Not committed (`cuno new` adds it to `.gitignore`) |
| User-level | `<cuno home>/config.toml` | All projects on that machine | — |

- Both hold machine-specific settings. Settings shared with the team go in `cuno.toml`.
- Precedence (higher wins):
  1. Command-line arguments
  2. Environment variables
  3. Project-level `.cuno/config.toml`
  4. `cuno.toml` (for items that can also be set in `cuno.toml`, e.g. `compiler`)
  5. User-level `<cuno home>/config.toml`
  6. Default values
- Settings decided by the project (`cuno.toml`) take precedence over personal global settings (user-level config).
- Exception: for coloring, `[term] color` in a configuration file takes precedence over the `NO_COLOR` environment variable ([commands.md](commands.md#available-for-all-commands)).
- cuno's environment variables (`CUNO_HOME`, `CUNO_COMPILER`, `CUNO_TARGET_DIR`) count as unset when their value is empty. `NO_COLOR` is the exception: it takes effect when set, even to an empty value ([commands.md](commands.md#available-for-all-commands)).
  - Rationale: in a POSIX shell, writing `CUNO_TARGET_DIR= cuno build` is how a variable is removed for that one run. For `NO_COLOR`, the convention shared across tools is that it takes effect even when empty.
- For the cuno home directory, see [distribution.md](distribution.md).

### A project's settings and trust

- The build commands, such as `cuno build`, and `cuno doctor` trust the settings kept in the project (`cuno.toml`, `.cuno/config.toml`). A tool written in `[toolchain.paths]` of `.cuno/config.toml` is run as written.
  - Rationale: the raw flags of `[build.<compiler>]` alone can make a compiler run arbitrary code, by loading a plugin for example. By the time it is built, a project is already trusted. Restricting tool paths alone would not make it safe, and would break projects that ship LLVM in their repository.
  - Checking `cuno.toml` and `.cuno/config.toml` before building someone else's project is the user's responsibility.
- The exception is `target-dir` in a layer kept in the project, which is limited to the project ([build.md](build.md#output-directory)). `cuno clean` deletes the output directory without running anything, so it is treated apart from building.

### Items

```toml
[build]
target-dir = "D:/fast/target"  # Output directory
jobs = 16                      # Number of parallel jobs
cache = "auto"                 # Build cache (auto / sccache / ccache / none)

[toolchain]
compiler = "clang"             # Compiler to use on this machine (msvc / clang / clang-cl / gcc / safec)

[toolchain.paths]              # Explicit tool locations (not needed if relying on auto-detection)
clang = "C:/LLVM/bin/clang.exe"
clang-format = "C:/LLVM/bin/clang-format.exe"
clang-tidy = "C:/LLVM/bin/clang-tidy.exe"

[target.aarch64-linux-android] # Per-target settings
ndk = "C:/Android/ndk/27.0"

[term]
color = "auto"                 # Coloring (auto / always / never)
verbose = false                # Whether to show verbose output (true / false)

[alias]                        # Command aliases
b = "build"
rr = "run --release"
```

#### `[build]`

| Item | Default | Description |
|---|---|---|
| `target-dir` | `target/` | Output directory ([build.md](build.md)) |
| `jobs` | Number of CPU cores | Number of parallel jobs |
| `cache` | `"auto"` | Build cache |

Values of `cache`:

- `auto`: Looks for sccache, then ccache, and uses whichever is found. If neither is found, no cache is used. Default.
- `sccache`: Uses sccache. Error if not found.
- `ccache`: Uses ccache. Error if not found.
- `none`: Does not use a build cache.

#### `[toolchain]`

| Item | Default | Description |
|---|---|---|
| `compiler` | none | Compiler to use on this machine. Same values as `compiler` in `cuno.toml`. At project level it takes precedence over `cuno.toml`; at user level it is overridden by `cuno.toml` ([toolchain.md](toolchain.md)) |

#### `[toolchain.paths]`

Write a location per tool name. Locations written here take precedence over auto-detection.

- `msvc`: Write the **installation directory** of Visual Studio (or Build Tools) (e.g. `"C:/Program Files/Microsoft Visual Studio/2022/Community"`). MSVC does not work with cl.exe alone, and cuno resolves the environment from that installation ([toolchain.md](toolchain.md)).
  - When it is written, only the Visual Studio in this directory is used (including the MSVC toolset that clang / clang-cl use). If no Visual Studio with the C++ x64 tools is found there, it is an error (exit code 3).
- `clang` / `clang-cl` / `gcc` / `safec` / `clang-format` / `clang-tidy` / `sccache` / `ccache`: Write the executable path.

#### `[target.<target>]`

For cross-compilation. Per target, write the locations of required tools, etc. (e.g. `ndk` for Android, `emsdk` for WebAssembly). The full set of items is an open question.

#### `[term]`

| Item | Default | Description |
|---|---|---|
| `color` | `"auto"` | Coloring. Same values as `--color`. Ranks below `--color` and above the `NO_COLOR` environment variable ([commands.md](commands.md#available-for-all-commands)) |
| `verbose` | `false` | Whether to show verbose output |

`verbose`:

- `true`: Always shows the same output as with `-v`. When `-q` is given, however, `-q` wins ([commands.md](commands.md#available-for-all-commands)).
- `false`: Normal output. Default.

#### `[alias]`

Command aliases (same as Cargo). Written as `alias = "expanded command"`. Existing command names cannot be overridden.
