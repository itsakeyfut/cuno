# 「複雑な設定は無理」説を検証し、cuno の線を引く

結論から言うと、「Xmake・build2・Conan は単純なケースは簡単だが、特殊・複雑な設定は困難か不可能で、大規模には向かない」という主張は、**3 つのツールのどれにもそのままでは当てはまらない**。Xmake で検証できた不満の中心は「書けない」ことではない。**欠けたファイルの黙殺、フラグの間引き・重複除去、警告の非表示、古いキャッシュ**のように、**成功と報告しながら間違っている**ことだった。build2 は逆で、保守者自身が「複雑」で CMake 利用者には「alien」だと認めており、単純なケースから難しい。Conan の痛みは CMake との継ぎ目と 1→2 移行に集中している。「大規模で使われない」は Xmake・Conan とも否定され、build2 は採用が少ないだけで技術的に破綻した証拠はない。「ドキュメント不足」は Xmake では成り立つ（実行順序や依存モデルなど意味論の記述不足と、検索性）。build2 と Conan では分量は足りていて、問題は難解さと「どの道を選ぶべきか分からない」ことだった。CMake からの移行で利用者が最も必要とするのは、自分の CMakeLists の翻訳ではない。**CMake でしか配布されていない依存を消費できること**である。そして調べた範囲では、**CMake の概念を自ツールの構文に対応づける公式の表を出しているツールは 1 つもない**。cuno への含意は 2 つある。逃げ道の設計で最も注意すべきは表現力の上限ではなく、黙って間違う経路（成功と報告しながら間違う、最も重い種類の失敗）を塞ぐことだということ。そして対応表は「以前は X と書いた、今は Y と書く」という課題指向の形にし、「対応なし」の行を明記すれば差別化になるということである。

証拠の格付けは次のとおり。具体的な issue・一次資料・保守者の発言で裏付けられたものは本文で事実として書く。具体性のない意見には【逸話】を付ける。調査者の背景知識で、今回取得した出典がないものには【未検証の背景知識】を付ける。Reddit は直接取得できず、検索スニペットかミラー経由になっている。

## Xmake の痛みは「書けない」ではなく「黙って違うことをする」

主張 (1) の前半は、Xmake については**条件付きで成り立つ**が、中身は主張と違う。最も詳細な批判は 2024-02-13 の David Chisnall によるものだ。彼は Xmake を CHERIoT RTOS（Xmake 公式の利用者一覧に載っているプロジェクト）で使っている。指摘は具体的である。**存在しないソースファイルは黙ってスキップされ、後でリンクエラーとして現れる**。警告は `-w` を付けない限り隠れる。`add_cflags` はコンパイラごとの許可リストにあるフラグしか通さず、カスタムツールチェーンからはそのリストを拡張できないため `{force = true}` が要る。`-Xclang` や `-mllvm` のように繰り返しが必要なフラグは**黙って重複除去され**、回避策は文書化されていない。コンパイラの更新がキャッシュの入力に入っておらず、`.xmake` を消す必要があった。ターゲット種別は文字列で、打ち間違えると暗黙のルールが黙って外れる ([Lobsters](https://lobste.rs/s/i2qnqj/why_cmake_sucks_2021))。UE4SS の貢献者も同じ方向の不満を書いている。再現性を「The biggest problem with xmake」と呼び、キャッシュのせいでクリーンや再クローンが要ること、**失敗が成功に見えることがある**ことを挙げた ([RE-UE4SS Discussion #471](https://github.com/UE4SS-RE/RE-UE4SS/discussions/471))。

複雑なケースが「不可能」だった例は見つからなかった。代わりに、**より新しい、またはより高度な API を保守者が issue で教える**というパターンが繰り返されている。`set_toolset("as","nasm")` では clang/gcc ツールチェーンが NASM に `-m64` を注入して失敗し、保守者は「古いインターフェース」だとして `add_toolchains("nasm")` を指示した（3.1.0 時点で未解決, [xmake#7729](https://github.com/xmake-io/xmake/issues/7729)）。STM32 向けの自作 `arm-none-eabi` ツールチェーンは 3.0.6 まで動き、3.0.7 で壊れた ([xmake#7532](https://github.com/xmake-io/xmake/issues/7532))。`add_requires("libsdl 2.28", "libsdl_ttf")` は libsdl を 2 版入れてしまい、直すには `add_requireconfs("**.libsdl", ...)` が要る。4 年間 Xmake を教えてきた SirLynix は、これを「requires advance knowledge of how xmake works」と評し、学生にとっては「advanced xmake usage」だと述べている ([xmake#5745](https://github.com/xmake-io/xmake/issues/5745))。逃げ道はあるが、そのたびに内部を知る必要がある。正確な不満は「複雑なことが不可能」ではなく、**逃げ道が発見しにくく、版によって変わる**ことである。

賞賛も具体的なものがある。UE4SS の議論では Xmake を推す声が 61% 対 38% で上回り、「If it works for you, it works on every other machine」と言われている ([UE4SS #471](https://github.com/UE4SS-RE/RE-UE4SS/discussions/471))。HN ではシェーダやアセット処理が CMake より楽だという声がある【逸話】([HN 46753037](https://news.ycombinator.com/item?id=46753037))。つまり再現性への評価は利用者の間で割れている。

大規模について。「大規模プロジェクトで使われていない」は**否定される**。Epic Games の Zen、Microsoft Research の CHERIoT RTOS、Cyber Engine Tweaks、LuisaCompute などが自己申告の利用者一覧に載っている ([who is using xmake](https://xmake.io/about/who_is_using_xmake.html))。ただし規模やビルドシステムの採用範囲は検証していない。「スケールしない」は**configure 時間について部分的に裏付けがあり、報告後に直された**。v3 では自明なターゲット 1000 個の `xmake config` に 87.78 秒かかった（CMake 2.73 秒、Meson 3.89 秒、xmake 2.9.9 では 30.63 秒）。保守者は原因を「1000 targets × 100 rules = 100,000 jobs」と説明し、jobgraph は「not been stress-tested」だったと認めて変更を戻した ([xmake#6775](https://github.com/xmake-io/xmake/issues/6775))。300 ターゲット・3000 ファイル超の規模では、`--files=` による単一ファイルのビルドが全ターゲットを走査して止まった ([xmake#5860](https://github.com/xmake-io/xmake/issues/5860))。どちらも原因は **Lua をターゲットごと・ルールごとに評価する configure 経路**にある。ビルド実行そのものが遅いという信頼できる報告はない。採用をためらう理由は、むしろ大規模事例の不足と作者がほぼ 1 人であること（バス係数）だった【逸話】([HN 46753037](https://news.ycombinator.com/item?id=46753037))。

## build2 は逆向き、Conan は継ぎ目で痛む

**build2 は主張と逆の形をしている**。保守者の Boris Kolpackov 自身が、build2 は「(unfortunately) complex」で多くの基本を「reimagines」しており、CMake 利用者には最初「alien」に見えると認めている ([Boost list 2024-04](https://listarchives.boost.org/Archives/boost/2024/04/256520.php))。公式 FAQ も、単純な単一プラットフォームのプロジェクトには「May be an overkill」で、主な用途は「complex, cross-platform C/C++」だと書いている ([build2 FAQ](https://build2.org/faq.xhtml))。複雑な設定（クロスコンパイル、コード生成、ターゲットごとのフラグ）が不可能だという、日付と具体性のある報告は見つからなかった。利用者の不満の多くは具体性に欠ける。「I'm already starting to hate it」【逸話】([Boost list](https://lists.boost.org/archives/list/boost@lists.boost.org/message/UKL5ESNYFGFUQTOQNXLPRXTSVSATAU6M))、「ugly DSL」【逸話・集約サイト経由】([saashub](https://www.saashub.com/build2)) といった類である。大規模については、build2 で構築している有名な大規模プロジェクトは見つからず、パッケージ数の少なさが繰り返し不満に挙がる【逸話】。一方で、技術的に規模で破綻したという証拠もない。採用が進まない理由は、依存をすべて build2 形式に移植しなければならないという鶏と卵の構造にあると読める。Packaging Guide も、上流のビルドシステムを包む手段は「no support」で、手で置き換えるしかないと明言している ([build2 Packaging Guide](https://build2.org/build2-toolchain/doc/build2-toolchain-packaging.xhtml))。

**Conan では主張 (1) が特定の形で成り立つ**。正規の流れで有名なパッケージを使うのは簡単だが、痛みは CMake との継ぎ目と移行に集まる。issue #17361 は「The documentation is unclear about the preferred way to integrate with CMake」と題し、CMakeDeps・CMakeToolchain・CMake・cmake_layout の使い分けが分からないと訴えている。保守者は 2 つの流れ（Conan 主導と、cmake-conan による CMake 主導）を説明した ([conan-io/conan#17361](https://github.com/conan-io/conan/issues/17361))。推奨のジェネレータは 2.25 で CMakeConfigDeps に移った ([Conan CMake tools](https://docs.conan.io/2/reference/tools/cmake.html))。レシピ作者の選択が利用者のビルドを縛る例もある。依存が対応していなければ CMakeDeps を使わない選択はできない ([SO archive](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/76222222/conan-2-0-use-cmake-toolchain-generator-without-cmakedeps))。cuno にとって最も示唆的なのは NixOS の事例だ。プロファイルの `platform_tool_requires` に `cmake` と `pkgconf` を挙げたのに、Conan は自前の CMake 3.30.5 と pkg-config を取得し、それが NixOS では動かなかった。投稿者は、設定に従うか、従えないならエラーにすることを期待していた ([NixOS Discourse](https://discourse.nixos.org/t/conan2-on-nixos-is-a-disaster/55231))。これも**設定と違うことを黙って行う**型の失敗である。1→2 移行の費用は具体的に記録されている。改行コードがレシピのハッシュに入るため Windows と Unix でリビジョンが変わる、`imports()` を `generate()` に移す、などである ([BIMcollab の移行記](https://ovaar.github.io/blog/conan-2x-migration-lessons-learned))。「大規模で使われない」は否定されるが、根拠は「Fortune 100 の多く」が使うというベンダー（JFrog）の自己申告や事例紹介が中心で、独立した大企業の事後報告は見つからなかった ([Introducing Conan 2.0](https://blog.conan.io/2023/02/22/Conan-2.0.html), [ACCU 2025](https://accu.org/video/spring-2025-day-2/rodriguezlosada))。

主張 (2) のドキュメントについてまとめると、成り立つのは **Xmake だけ**である。それも不満は API リファレンスの量ではない。**意味論**が書かれていないことだ。Chisnall の言う「The execution order is not actually documented anywhere」や「their dependency model is totally undocumented」がそれにあたる ([Lobsters](https://lobste.rs/s/i2qnqj/why_cmake_sucks_2021))。加えて Google の索引が弱いこと ([UE4SS #471](https://github.com/UE4SS-RE/RE-UE4SS/discussions/471))、`os.argv()` のような個別の欠落 ([xmake#6919](https://github.com/xmake-io/xmake/issues/6919)) もある。2025 年の VitePress 移行では、API 索引ページが「inconvenient to maintain」として削除され、llms.txt に置き換えられた ([xmake-docs#227](https://github.com/xmake-io/xmake-docs/issues/227))。支援の知識の多くは中国語の issue にある。build2 の文書は分量が多く（ビルドシステムのマニュアル、PDF 版、モジュールごとの文書, [build2 Documentation](https://build2.org/doc.xhtml)）、「不足」は当たらない。ただし Roseman Labs は、Boost のリンク方法のような実務で build2 の文書が「not sufficiently approachable」だとして候補から外した ([Roseman Labs](https://techblog.rosemanlabs.com/c++/build-systems/2021/02/22/c++-build-systems-our-transition-from-cmake-to-meson.html), 2021)。Conan の文書は版ごとに大量にあり、問題は推奨の道が複数あって、しかも動くことである。比較のために言えば、CMake 自身の文書も「a reference not a tutorial」と批判されている ([r/cpp](https://red.ks32.dev/r/cpp/comments/1jmbekf/comment/mkblzew), [Kitware issue 25498](https://gitlab.kitware.com/cmake/cmake/-/issues/25498))。文書の量ではなく、**モデルの説明と、道が 1 本であること**が効いている。

## 大規模プロジェクトの本当の要求と、Meson と Bazel の線引き

一次資料で裏付けられた「なぜ複雑な設定が要るか」は 2 件ある。Godot は、生成されるファイル（binders）、解析されるファイル（shaders）、カスタマイズ（plugins）のために「complex logic which is easier to write in an actual programming language」が要ると書いている。また開発者は複数のプラットフォームとターゲットを再設定なしで同時にビルドする必要がある ([Godot 3.1 docs](https://docs.godotengine.org/en/3.1/development/compiling/introduction_to_the_buildsystem.html), 2019 年頃の文書)。PostgreSQL は、autoconf の保守の難しさと、再帰 make の「hard to resolve dependency issues and slow builds」を理由に Meson を加え、MSVC 専用ビルドの廃止を計画した ([pgsql-committers](https://www.postgresql.org/message-id/E1obF3v-001S9d-UD%40gemulon.postgresql.org))。ただし autoconf/make は残り、2025 年 12 月にも autoconf の更新が議論されている ([pgsql-hackers](https://www.postgresql.org/message-id/CAJ7c6TMDGXMXPXnEM5yz4%3D4wdYXeVSYswJOeFpspa1bH5xsxNA%40mail.gmail.com))。2 件に共通するのは、**ビルドシステムの選択が最も難しい要求で決まり、移行には何年も 2 つのシステムが並走する**ということだ。要求の残りの目録は次のとおり【未検証の背景知識】。コード生成（LLVM の TableGen、Qt の moc/uic/rcc、protobuf）、ファイルごとのフラグ（SIMD カーネルを `-mavx2` で別にコンパイルする、取り込んだサードパーティの警告を切る）、クロスコンパイルとカスタムツールチェーン（Chromium の GN、Android NDK、組み込み）、言語の混在（nasm、CUDA、Rust）、ビルド済みバイナリの依存、プラットフォーム条件付きのソース、PCH とユニティビルド、install/export、IDE 連携。

調査データは、痛みがビルド言語よりも依存とビルド時間に集中していることを示す。ISO C++ 2024 調査では、「依存ライブラリの管理」を大きな痛みとする回答が **45.43%**、ビルド時間が **42.86%**、「CMake プロジェクトの管理」が **30.38%** だった。ビルドツールの利用率は CMake **83.24%**、Bazel 9.98%、Meson 5.99% である ([CppDevSurvey 2024](https://isocpp.org/files/papers/CppDevSurvey-2024-summary.pdf))。依存の入手方法として最も多いのは「ライブラリのソースを自分のビルドに含める」で、**68.54%** だった（同上。表は崩れた PDF テキストから整列し直したもので、Conan/vcpkg の対応は最も不確か）。この 68.54% は、取り込んだソースを独自のフラグで、警告を切ってビルドする需要が大きいことを意味する。2025 年の自由記述の要約で最大の要望は、「Rust's Cargo」のような標準のパッケージ管理とビルドシステムだった ([CppDevSurvey 2025](https://isocpp.org/files/papers/CppDevSurvey-2025-summary.pdf))。

Meson は cuno に最も近い前例である。言語は「intentionally not Turing complete」で、ユーザー定義関数と一般的なループを禁じ、複雑な処理は外部スクリプトに追い出す ([Meson FAQ](https://mesonbuild.com/FAQ.html))。グロブも「cannot be made both reliable and fast」として禁じている（同 FAQ）。PCH ([Precompiled headers](https://mesonbuild.com/Precompiled-headers.html)) とユニティビルド ([Unity builds](https://mesonbuild.com/Unity-builds.html)) は宣言的に書ける。利用者の摩擦は**唯一の逃げ道である `custom_target`** に集中している。1 ターゲットにつきコマンドは 1 つだけ ([Custom build targets](https://mesonbuild.com/Custom-build-targets.html))。シェルを通さないため `&&` が Windows で失敗する ([gtk-rust-template #46](https://gitlab.gnome.org/World/Rust/gtk-rust-template/-/issues/46))。出力はビルドディレクトリにしか置けない ([meson #5434](https://github.com/mesonbuild/meson/issues/5434))。コマンド引数に生で渡したライブラリは追跡されない ([meson #4892](https://github.com/mesonbuild/meson/issues/4892))。そして**コマンドが実行されなかったのにビルドはエラーを出さなかった**という報告がある ([mesonbuild Google Group](https://groups.google.com/g/mesonbuild/c/LhHq37hWy9A), 日付未確認)。拡張性のなさを「all hardcoded」と嫌う声もある【逸話】([Fedora devel](https://lists.fedoraproject.org/archives/list/devel@lists.fedoraproject.org/message/BBWXTDVI24PYCDNGRV7RCGXHRJPBYUPN))。ファイルごとのフラグは書けず、別の static_library に分けるのが定石だという点は【未検証の背景知識】。

Bazel はほぼすべてを宣言的に書けるが、その費用が際立つ。C++ ツールチェーンの設定には `cc_toolchain` と、`CcToolchainConfigInfo` を返す Starlark ルールが要り、action と feature を区別する必要がある ([Bazel C++ Toolchain Configuration](https://bazel.build/docs/cc-toolchain-config-reference?hl=en))。チュートリアルは `--crosstool_top` からツールチェーン解決へと移り変わっている ([current tutorial](https://bazel.build/tutorials/ccp-toolchain-config))。Windows の設定は Bazel 7 と 8、Bzlmod と WORKSPACE で異なる ([Using Bazel on Windows](https://bazel.build/docs/windows))。compile_commands.json はネイティブには出ず、第三者の抽出ツールに頼る ([hedronvision](https://github.com/hedronvision/bazel-compile-commands-extractor))。HN では、大組織で専門家になるには 3〜5 人の専任が要るという声、約 6 人月の導入という声、専任なしの約 20 人チームでビルド時間が 92% 減ったという声が並ぶ【逸話】([HN: Bazel 8.0](https://news.ycombinator.com/item?id=42370744))。cuno にとっての教訓は 2 つある。`select()` のように**閉じた集合のプラットフォーム属性で分岐する**方式は、宣言的なファイルと最も相性がよい。逆に C++ ツールチェーン設定は最も真似すべきでない部分である。

| 要求 | Xmake | build2 | Conan | Meson | Bazel |
|---|---|---|---|---|---|
| カスタムツールチェーン／クロス | 書けるが API が変わり、版で壊れた (#7729, #7532) | 最初から組み込み（保守者の主張） | 設定の場所がプロファイルと CMake の 2 か所 | machine file で宣言的 | 書けるが最難関 |
| コード生成 | Lua のスクリプト領域で強い | 不明（証拠なし） | 対象外（ビルドは CMake 側） | `custom_target` に摩擦 | genrule か Starlark |
| フラグの扱い | 許可リストによる間引き、重複除去 | 不明 | 対象外 | ターゲット単位 | `copts` |
| 規模 | configure 時間（修正済み） | 証拠なし | ベンダーの主張で大規模 | 証拠なし | 強みだが人的費用が大きい |
| 文書 | 意味論が欠落 | 量は十分、難解 | 量は十分、道が複数 | 評判は良い (SciPy) | 版ごとの差異 |

## 移行者が求めるのは翻訳ではなく CMake 資産の消費

主張 (4) の前半の答えは、**CMake に残る理由は、依存が CMake の config パッケージを出していて `find_package` がたいてい動くことにある**、である。「Cargo-like build tool for C/C++」の Show HN では、新しいツールは CMake でビルドされるプロジェクトを依存として消費できなければならない、CMake のコンパイラ癖の吸収を再実装する必要がある、pkg-config と CPS に対応してほしい、といった意見が出た【逸話の集合】([HN 47705413 mirror](https://hn.nuxt.dev/item/47705413))。CMake を離れた側の理由は、脆さと、使いこなしている実感が持てないことだった。Roseman Labs は Modern CMake で書き直しても脆く、「never felt they had mastered CMake」と書いている ([Roseman Labs](https://techblog.rosemanlabs.com/c++/build-systems/2021/02/22/c++-build-systems-our-transition-from-cmake-to-meson.html))。SciPy は Meson を選んだ理由の 1 つに「great documentation (unlike CMake)」を挙げた ([Quansight Labs](https://labs.quansight.org/blog/moving-scipy-to-meson))。反例として、Snes9x は Meson から CMake に戻っている ([keasigmadelta](https://keasigmadelta.com/?p=8890))。移行の阻害要因を定量的に調べた調査は見つからなかった。

後半の問いには、**どのツールも CMake のコマンドを自ツールの構文に対応づける公式の表を持っていない**と答えられる。あるのは 3 つの形式だけだ。1 つ目は CMake を消費する相互運用で、Meson の `cmake.subproject()` と `dependency(..., method: 'cmake')` ([CMake module](https://mesonbuild.com/CMake-module.html), [Dependencies](https://mesonbuild.com/Dependencies.html))、Xmake の `add_requires("cmake::ZLIB", ...)` ([using system packages](https://xmake.io/guide/package-management/using-system-packages.html))、Bazel の rules_foreign_cc ([cmake docs](https://bazel-contrib.github.io/rules_foreign_cc/cmake.html)) がある。2 つ目は骨組みの自動変換で、Meson の `cmake2meson.py` は「data models differ greatly」として骨組みしか作らないと明言している ([Build system converters](https://mesonbuild.com/Build-system-converters.html))。Bazel 向けには第三者の rebaze がある。3 つ目は手作業の移植ガイドで、build2 の Packaging Guide がこれにあたる。Bazel の公式移行ページは Maven と Xcode しか扱っていない ([bazel.build/migrate](https://bazel.build/migrate))。変換器が自ら「変換できない」と挙げているのは、条件分岐・ループ・関数／マクロ・キャッシュ変数・親スコープ変数・ディレクトリをまたぐターゲット変更・評価なしの `find_package` である ([rebaze CMake tutorial](https://albertocavalcante.github.io/rebaze/tutorials/cmake))。rebaze は CMakeLists を静的に解析する代わりに CMake File API の codemodel を読む道も用意しており、その一方で pthread や m のようなシステムライブラリを**黙って無視する** ([dependency mappings](https://albertocavalcante.github.io/rebaze/guides/dependency-mappings))。Meson の CMake 取り込みは generator expression を「ignores most of them」としている ([Meson cmake/generator.py](https://qemu.googlesource.com/meson/+/refs/heads/1.1/mesonbuild/cmake/generator.py))。どの資料も明示的に対応づけていない概念は次のとおり。PUBLIC/PRIVATE/INTERFACE の伝播（CMake の定義は [target_link_libraries](https://cmake.org/cmake/help/v4.0/command/target_link_libraries.html)）、generator expression、`option()` とキャッシュ変数、presets、install/export、`add_custom_command`。これは読んだページに無かったことからの推論で、全ページは確認していない。

## cuno の方針: 閉じた宣言、うるさい逃げ道、課題指向の対応表

証拠が最も強く支える方針は、**複雑さへの入口ごとに「黙って違うことをする」経路を設計段階で塞ぐ**ことだ。Xmake・Conan・Meson・rebaze で検証できた不満のうち最も重いものは、すべて、成功と報告しながら間違う種類の失敗である。存在しないファイルのスキップ、フラグの間引き・重複除去、警告の非表示、コンパイラ更新を無視するキャッシュ、設定に反したツールの取得、実行されないカスタムコマンド、黙って無視されるライブラリである。cuno の現在の仕様はこの方向とすでに合っている。未知のキーの扱いを定め（manifest.md「未知のキー」）、`links` に `.lib` を付けるとエラーにし、`[build.<compiler>].flags` は生のまま渡すと書いている。今後、層を足すたびに守るべき具体的な規則は次のとおりである。

**1 層目（宣言）**: 条件は `[platform.<OS>.build]` と `[profile.<name>.build]` の閉じた名前付きの表に限り、`cfg(...)` のような式は入れない。これは Bazel の `select()` のうち宣言と相性のよい部分と、Meson の「関数もループもない」という線を合わせたもので、現行の manifest.md の判断と一致する。この線を守っている間、失敗は、利用者が読めるエラーで止まる範囲に収まる（未知のキーはエラーになり、利用者が読めるメッセージで止まる）。**ファイルごとのフラグ**（SIMD カーネル、取り込んだサードパーティの警告を切る）は、ISO 調査の 68.54% というソース同梱の割合から見て、遅かれ早かれ必要になる。Meson は書けず、別ライブラリに分けるのが定石だという話は【未検証の背景知識】。cuno が対応するなら、グロブに対する名前付きの上書き表のように閉じた形にし、一致するファイルが 0 件ならエラーにすべきである。0 件を黙って通すと、Xmake の「欠けたファイルのスキップ」と同じ、黙って間違う失敗になる。

**2 層目（`[[build.rule]]`）**: Meson の `custom_target` の摩擦がそのまま設計の確認項目になる。command をシェル文字列にするか引数の配列にするか（シェル文字列は Windows で `&&` の問題を生む）。1 ルールで複数のコマンドを許すか。宣言した出力が生成されなければエラーにするか（「実行されなかったのに成功」を防ぐ）。入力のグロブが 0 件のときと、ファイルが増えたときの再評価をどうするか。build.md の例 `command = "glslc {in} -o {out} ..."` は文字列なので、この点はまだ決まっていないと読める。Meson はグロブ自体を「reliable and fast を両立できない」として禁じた。グロブを許す cuno は、新しいファイルを検出しないと古い成果物を実行するという、黙って間違う失敗を抱えることになる。

**3 層目（Lua）**: Xmake から学べる費用は 3 つある。1 つ目は**評価の段階と順序を文書化しないと、逃げ道が当て推量になる**こと（「execution order is not actually documented anywhere」）。2 つ目は**スクリプトをターゲットごと・ルールごとに評価すると configure 時間を支配する**こと (#6775)。3 つ目は **API の変化で自作ツールチェーンが patch リリースで壊れる**こと (#7532)。build.md がすでに挙げている「API はバージョン付きで提供する」という対策は、この 3 つ目への直接の答えになっている。加えて、スクリプトから組み込みの処理を再利用できるようにすることも勧める。Chisnall はそれができないことを批判していた。スクリプトが宣言を黙って上書きできないようにすることも、黙って間違わないための要件として仕様に書く価値がある。

**学習量を小さく保つ**ことについて、証拠が支えるのは「新しい概念を最初の成功の前に要求しない」ことである。build2 は hello-world の段階で概念の距離という代償を払っている。Conan は推奨の道が複数あり、しかも動いた。そのため文書は API の一覧より先に、**層をどう重ね合わせるか、いつ何が評価されるか、という意味論を 1 ページで**示すべきである。manifest.md の「設定の重ね合わせ」は、この形の良い先例になっている。

**CMake から cuno への対応表**は、自動変換器ではなく**課題指向の表**にすべきである。根拠は 3 つある。変換器は骨組みしか作れないと各ツールが自ら認めていること。CMake の文書は「参照で、指南ではない」と批判されていること。そして公式の対応表がどのツールにも存在しないことだ。各行は「CMake で X と書いていた → cuno.toml では Y」とし、**対応のない概念には「対応なし、代わりに Z」という行を明示する**。対象は、どの資料も対応づけていない PUBLIC/PRIVATE/INTERFACE、`$<CONFIG:>` や compiler-id の generator expression（→ `[profile.*.build]` と `[build.<compiler>]`）、`option()`/キャッシュ変数、presets、install/export、`add_custom_command`（→ `[[build.rule]]`）、`find_package` である。ただし移行の最大の障害は CMake の依存を消費できるかどうかであり、それに答えるのは対応表ではなく M7 のレシピの仕組み（裏で CMake を呼ぶ）である。対応表の `find_package` の行は「M7 まではシステムライブラリの `links` だけ」と正直に書かないと、利用者は cuno ができないことに途中で気づくことになる。なお、commands.md は cuno 自身の出力で CMake を名指しすることを禁じているが、これは出力についての規則であり、利用者向けの文書の対応表とは衝突しない。

## 結論

この調査で変わった理解は、「複雑な設定を許すか」という問いの重心である。証拠が示しているのは、宣言的なツールが複雑なケースで**書けずに止まる**ことよりも、逃げ道や既定値が**黙って間違う**ことの方が利用者の信頼を深く損なう、ということだった。止まる失敗は利用者が気づいて直せるが、黙って間違う失敗は気づかれない。したがって cuno が逃げ道を増やすときに比べるべきなのは表現力ではない。各入口で「0 件」「出力なし」「上書き」「キャッシュの鍵からの漏れ」がエラーになるかどうかである。

もう 1 つ、CMake からの移行支援は、cuno の「CMake と共存しない」という方針と一見矛盾するように見えて、実はしない。移行者が求めているのは CMakeLists の翻訳ではなく、CMake の世界にある依存の消費だからだ。それをレシピが裏で吸収し、利用者向けには「対応なし」まで書いた対応表を出す。この組み合わせは、調べた範囲では先行するツールが埋めていない隙間である。未解決のまま残るのは次の点だ。ファイルごとのフラグが現実にどれほど必要とされるかには定量的な裏付けがない。build2 で複雑なケースがどう扱われるかを示す具体的な報告がない。Conan の package_id／互換性に関する近年の不満は今回集められなかった。
